Easy CMS เริ่มจาก headless CMS ที่อยู่ในแอป Nuxt หรือ Next.js และกำลังกลายเป็น backend TypeScript ทั้งตัว ([ผมเล่าเรื่องนี้ไว้ที่นี่](/th/blog/more-than-a-cms-th)) ส่วนที่สำคัญที่สุดของ backend และพลาดง่ายที่สุดด้วย คือกฎว่าใครทำอะไรได้บ้าง

บทความนี้เล่ากฎเหล่านั้นใน Easy CMS 1.48.0: กฎ access ในโค้ดที่คืน query แทนคำตอบใช่หรือไม่ใช่ได้ บทบาทที่ admin ติ๊กเองในหน้าแอดมินได้ลึกถึง field เดียว เอกสารที่มีเจ้าของ และ API key รวมถึงการตัดสินใจข้อเดียวที่ยึดทุกอย่างไว้ด้วยกัน คือทุกช่องทางที่เข้าถึงข้อมูลต้องผ่านการตรวจชุดเดียวกัน

## ชั้นที่ 1: กฎ access ในโค้ด

ทุกอย่างเริ่มใน config ในรูปของฟังก์ชัน:

```ts
import { defineConfig, isAdmin, isStaff } from '@easy-cms/core'

export default defineConfig({
  collections: [
    {
      slug: 'posts',
      drafts: true,
      access: {
        // ผู้เข้าชมเห็นเฉพาะที่เผยแพร่แล้ว ผู้ที่ login เห็นทั้งหมด
        read: ({ user }) => (user ? true : { status: { equals: 'published' } }),
        create: isStaff,
        // admin แก้ได้ทุกบทความ คนอื่นแก้ได้เฉพาะของตัวเอง
        update: ({ user }) => (user?.role === 'admin' ? true : user ? { author: { equals: user.id } } : false),
        delete: isAdmin,
      },
      fields: [
        { name: 'title', type: 'text', required: true },
        { name: 'author', type: 'relationship', to: 'users' },
        { name: 'featured', type: 'boolean', access: { update: ({ user }) => user?.role === 'admin' } },
      ],
    },
  ],
})
```

กฎแต่ละข้อได้ `{ user, id?, data? }` และคืนได้ทั้ง `true`/`false` หรือ **where query** แบบหลังนี่แหละคือสิทธิ์รายแถว (row-level) สำหรับ `read` where จะถูกต่อเข้ากับทุก query ผลลัพธ์ของผู้เข้าชมจึงถูกกรองในฐานข้อมูล ไม่ใช่กรองทีหลัง ส่วน `update` และ `delete` เอกสารต้องตรงกับ where นั้น `create` ต้องคืน boolean เท่านั้น เพราะยังไม่มีเอกสารให้เทียบ

มีรายละเอียดสองข้อที่มาจากการคิดว่า id หนึ่งตัวบอกอะไรผู้โจมตีได้บ้าง การแก้หรือลบเอกสารที่ผู้ใช้ไม่มีสิทธิ์แม้แต่จะอ่านจะได้ `404` เหมือน id ที่ไม่มีอยู่จริง ส่วนเอกสารที่อ่านได้แต่แก้ไม่ได้จะได้ `403` การไล่เดา id จึงไม่บอกอะไรเลยว่ามีเอกสารอะไรอยู่

อีกข้อคือค่าเริ่มต้น ถ้า collection ไม่มีกฎของ operation ไหน จะอนุญาตเฉพาะผู้ใช้หน้าแอดมินที่ login แล้ว เนื้อหาสาธารณะต้องตั้งใจทำให้เป็นสาธารณะ ด้วย `read: () => true` หรือ helper `anyone` ผมยอมให้มีคนถามว่า "ทำไมผู้เข้าชมมองไม่เห็น" ดีกว่าให้ใครมารู้ทีหลังว่าฉบับร่างของตัวเองเปิดสาธารณะอยู่

### field

field มีกฎ `read`, `create` และ `update` ของตัวเอง field ที่อ่านไม่ได้จะไม่อยู่ใน response และไม่อยู่ในหน้าแอดมิน field ที่แก้ไม่ได้จะถูกข้ามเมื่อส่งมา และแสดงเป็นอ่านอย่างเดียว `create` บอกว่าใครตั้งค่า field ได้ตอนสร้างเอกสาร ถ้าไม่มีจะใช้ `update` แทน กรณี "ใครก็กรอกได้ครั้งแรก แต่แก้ทีหลังได้แค่ admin" จึงเขียนแค่สองบรรทัด

ต่างจากกฎระดับ collection กฎของ field ตอบได้แค่ใช่หรือไม่ใช่ ตัวตรวจใน `access-control.ts` นับเฉพาะ `true` จริงๆ ว่าอนุญาต การคืน where จากกฎของ field จึงเท่ากับไม่อนุญาต

ตรงนี้เองที่ผมเจอช่องโหว่ของตัวเอง ก่อน 0.34 `access.read` ของ field แค่ซ่อนค่าจาก response แต่ยังใช้ field นั้นกรองได้ ลองนึกถึง field `salary` ที่คุณอ่านไม่ได้: `?where[salary][gt]=100000` ยังตอบกลับมาเป็นรายการที่สั้นลง และ request แบบนี้ไม่กี่ครั้งก็เดาค่าได้แล้ว ตอนนี้ field ที่อ่านไม่ได้ใช้กรองหรือเรียงไม่ได้ด้วย ได้ `403` ทั้งกับกฎในโค้ดและ field ที่ซ่อนด้วยบทบาท การแก้นี้ทำให้ตัวกรองที่บางโปรเจกต์เคยใช้อยู่พัง ซึ่ง [ADR-0037](https://github.com/maritonx/easy-cms/blob/main/docs/adr/0037-own-documents-and-field-permissions.md) เขียนไว้เป็นผลที่ตามมา ผมคิดว่าคุ้ม

## ชั้นที่ 2: บทบาทในหน้าแอดมิน

กฎในโค้ดเหมาะกับสิ่งที่เป็นจริงของตัวผลิตภัณฑ์ เช่น "ผู้เข้าชมเห็นบทความที่เผยแพร่แล้ว" แต่ไม่เหมาะกับสิ่งที่เป็นจริงของทีมในเดือนนี้ เช่น "ทีมแปลแก้หน้าได้แต่ลบไม่ได้" การเปลี่ยนเรื่องแบบนี้ไม่ควรต้อง deploy

ตั้งแต่ 0.33 จึงเปิดบทบาทได้ด้วยบรรทัดเดียว:

```ts
auth: { roles: ['admin', 'editor', 'author'], rbac: true },
```

จากนั้น admin จะได้หน้า **Settings → Roles** เพิ่มบทบาทได้ คัดลอกบทบาทเดิมเป็นจุดเริ่มต้นได้ และติ๊ก **อ่าน, สร้าง, แก้ไข, ลบ** และ **เผยแพร่** ของแต่ละ collection และ global รวมถึงหน้าในแอดมินที่บทบาทนั้นเห็น (สถานะระบบ, Deliveries, งานเบื้องหลัง, หน้าและกล่องบนแดชบอร์ดของ plugin) ส่วน Backups, Email และ Roles เป็นของ admin เท่านั้น เพราะไฟล์ backup มีทั้งฐานข้อมูล และหน้า Email ส่งอีเมลออกจากเว็บได้

การตัดสินใจที่กำหนดทุกอย่างที่เหลือคือ **ผู้ใช้ทำอะไรได้ก็ต่อเมื่อทั้งโค้ดและบทบาทอนุญาต** โค้ดเป็นเพดานเสมอ บทบาททำได้แค่บีบให้แคบกว่าที่กฎ access อนุญาต ขยายเกินไม่ได้ กฎ "ผู้เขียนแก้ได้เฉพาะบทความของตัวเอง" ในโค้ดจึงยังทำงานไม่ว่า admin จะติ๊กอะไร และไม่มีใครติ๊กข้ามกฎที่นักพัฒนาเขียนไว้ได้

จากข้อนั้นจึงได้กฎตามมาอีกไม่กี่ข้อ:

- admin (`role: 'admin'`) ทำได้ทุกอย่างเสมอ และบทบาทนี้แก้หรือลบไม่ได้
- ผู้เข้าชมที่ไม่ได้ login ใช้กฎ access อย่างเดียว `read: () => true` จึงยังเป็นสาธารณะ
- ทุกคนยังมีหน้าบัญชีของตัวเองเสมอ ไม่ว่าจะมีบทบาทอะไร
- บทบาทที่อยู่ใน `auth.roles` เปลี่ยนชื่อและติ๊กใหม่ได้แต่ลบไม่ได้ เพราะโค้ดของคุณอาจเทียบ `user.role === 'editor'` อยู่

ข้อแลกเปลี่ยนที่ผมคิดนานที่สุดคือ collection ใหม่ควรเป็นของใคร ตอนเปิดบทบาทครั้งแรก ทุกบทบาทได้ทุกอย่างที่เคยทำได้ การเปิดบทบาทจึงไม่เปลี่ยนอะไรจนกว่าจะมีคนเอาติ๊กออก แต่ collection ที่เพิ่มเข้า config ทีหลังจะ **ไม่ให้บทบาทไหนเลย** มีแค่ admin ที่เห็นจนกว่าจะมีคนติ๊ก และหน้า Settings → Roles จะติดป้าย **ใหม่** ไว้ เรื่องนี้ทำให้คนหงุดหงิดได้ deploy collection ไปแล้ว editor มองไม่เห็น แต่อีกทางเลือกคือ collection ที่เก็บข้อมูลอ่อนไหวโผล่ให้ editor ทุกคนเห็นทันทีที่ deploy ซึ่งผมไม่อยากเลือก

บทบาทถูก cache ในหน่วยความจำ การแก้จะล้าง cache ของ instance ที่แก้ ส่วน instance อื่นอ่านบทบาทใหม่อย่างน้อยทุก 30 วินาที ถ้ามีหลายเซิร์ฟเวอร์ ติ๊กที่เอาออกอาจใช้เวลาถึงครึ่งนาทีกว่าจะมีผลทุกเครื่อง

### ลงไปถึง field เดียว

**Fields ›** ในแถวของบทบาทจะเปิด field ของ collection นั้น แต่ละตัวตั้งเป็น **แก้ไขได้**, **อ่านอย่างเดียว** หรือ **ซ่อน** ได้ field ที่ไม่ได้ตั้งจะตามสิทธิ์ของแถว field ที่เพิ่มทีหลังจึงทำงานเหมือนตัวอื่น field ที่ซ่อนจะไม่ถูกส่งกลับ และใช้กรองหรือเรียงไม่ได้ด้วยเหตุผลเดียวกับข้างบน ส่วน field อ่านอย่างเดียวแสดงได้แต่ไม่บันทึกค่าที่ส่งมา

มีตัวกันอยู่ข้อหนึ่ง: field ที่บังคับกรอกและไม่มีค่าเริ่มต้นจะตั้งเป็นอ่านอย่างเดียวหรือซ่อนไม่ได้ สำหรับบทบาทที่สร้างเอกสารได้ ไม่อย่างนั้นบทบาทนั้นจะสร้างเอกสารไม่ได้เลย

## เอกสารที่มีเจ้าของ

กฎที่คนขอมากที่สุดไม่ใช่ระดับ field แต่เป็น "นักเขียนอ่านได้ทุกบทความ แต่แก้ได้แค่ของตัวเอง" เมื่อเปิดบทบาท เรื่องนี้เป็นแค่ปุ่มเดียว: ข้างช่อง อ่าน แก้ไข ลบ หรือเผยแพร่ ที่ติ๊กไว้ มีปุ่มรูปคนสำหรับจำกัดให้ทำได้เฉพาะ **เอกสารของตัวเอง**

การทำแบบนั้นต้องรู้ก่อนว่าใครเป็นเจ้าของเอกสาร ซึ่งเดิม Easy CMS ไม่รู้ versions เก็บว่าใครบันทึกอะไรก็จริง แต่เฉพาะ collection ที่เปิด versions เมื่อเปิดบทบาท ทุก collection ยกเว้น Users จึงได้ field `createdBy` ที่ Easy CMS ตั้งให้ตอนสร้างเอกสาร request ตั้งหรือแก้ค่านี้ไม่ได้ ส่วน Local API แบบ trusted ตั้งได้ การ import จึงเก็บผู้เขียนจริงไว้ได้

หลายครั้งเจ้าของคือ field ที่มีอยู่แล้ว เช่นผู้เขียนบทความ:

```ts
{
  slug: 'posts',
  admin: { ownerField: 'author' }, // relationship ไปที่ users แบบค่าเดียว
  fields: [{ name: 'author', type: 'relationship', to: 'users' } /* … */],
}
```

field เจ้าของที่ว่างจะถูกเติมเป็นคนที่สร้างเอกสาร บทบาทที่ได้แค่เอกสารของตัวเองจะเห็น field นี้เป็นอ่านอย่างเดียว จึงยกเอกสารให้คนอื่นหรือแย่งของคนอื่นไม่ได้ เบื้องหลัง "เฉพาะของตัวเอง" ก็คือสิ่งเดียวกับชั้นที่ 1: where `{ author: { equals: user.id } }` ที่บทบาทเติมให้แทนโค้ดของคุณ

หน้ารายการในแอดมินมีตัวกรอง **ของฉัน** การลบผู้ใช้จะถามว่าใครรับเอกสารที่เขาเป็นเจ้าของ หรือไม่ให้ใคร (REST คือ `DELETE <api>/users/:id?transferTo=<id>`) เอกสารที่มีอยู่ก่อนเปิดบทบาทได้ `createdBy` จากคนที่บันทึก version แรก ถ้ามีประวัติ ที่เหลือไม่มีเจ้าของ จึงแก้ได้เฉพาะบทบาทที่ได้เอกสารทั้งหมด

## API key ที่ไม่มีวันได้สิทธิ์เกินเจ้าของ

สคริปต์ แอปอื่น และ AI agent ไม่ควรใช้รหัสผ่านของใคร ให้ใช้ API key แทน (`apiKeys: true` แล้วไปที่ **Settings → API keys**)

ผมเคยเรียกสิ่งนี้ว่า "API key ใต้บทบาท" รวมถึงในบทความที่แล้วด้วย ซึ่งใกล้เคียงแต่ไม่ตรงกับการทำงานจริง ขอพูดให้ชัดตรงนี้ key ไม่มีบทบาทของตัวเอง **key เป็นของผู้ใช้คนหนึ่ง และแคบกว่าผู้ใช้คนนั้นเสมอ** key ระบุสิ่งที่ทำได้ต่อ collection และ global (อ่าน สร้าง แก้ไข ลบ เผยแพร่) และทุก request Easy CMS ตรวจทั้งรายการของ key, กฎ access ของเจ้าของ และบทบาทของเจ้าของเมื่อเปิดบทบาท ถ้าสัปดาห์หน้าบทบาทของเจ้าของเสียสิทธิ์ลบ ทุก key ที่เขาสร้างก็เสียสิทธิ์นั้นด้วย โดยไม่ต้องมีใครไปแก้ key และหน้าแอดมินให้ติ๊กได้เฉพาะสิ่งที่เจ้าของทำได้

คำตอบบอกสคริปต์ว่าชั้นไหนเป็นคนปฏิเสธ:

| คำตอบ | เมื่อไร |
|---|---|
| `401 Invalid or expired API key` | key ผิด ถูกลบ หมดอายุ หรือเจ้าของถูกปิดใช้งาน |
| `403 This API key may not create "posts"` | key ไม่ได้ระบุการกระทำนั้น |
| `403 Forbidden` | key ระบุไว้ แต่กฎของเจ้าของไม่อนุญาต |

key ที่ใช้ไม่ได้ได้ `401` แทนที่จะถูกนับเป็นผู้เข้าชมเงียบๆ สคริปต์ที่ key ถูกเพิกถอนจึงล้มให้เห็นทันที ไม่ใช่อ่านได้แค่เนื้อหาสาธารณะแล้วทำต่อไปเหมือนไม่มีอะไร

มีบางอย่างที่ไม่มี key ไหนทำได้ ไม่ว่าจะระบุอะไรไว้: อ่านหรือแก้ users, อ่านหรือแก้ key และสร้าง key ใหม่ key ที่มีสิทธิ์สร้างและแก้แต่ไม่มีสิทธิ์เผยแพร่จะเขียนเป็นฉบับร่างให้คนมาตรวจและเผยแพร่ และกฎของคุณเองก็แยก key ออกได้ เพราะ user ของ request มี `apiKey`:

```ts
access: {
  // คนลบบทความได้ แต่ key ลบไม่ได้ ไม่ว่าจะระบุอะไรไว้
  delete: ({ user }) => !!user && !user.apiKey,
}
```

สิ่งที่พลาดตรงนี้เล็กกว่าแต่เกิดขึ้นจริง key ยังใช้ได้หลังเปลี่ยนรหัสผ่าน ซึ่งเป็นสิ่งที่สคริปต์ต้องการ แต่หลังจากรีเซ็ตรหัสผ่านที่ลืม คนที่มีรหัสเก่าอาจสร้าง key ไว้แล้ว ตอนนี้หลังรีเซ็ต หน้าแอดมินจึงแสดง key ของคุณก่อนและเสนอให้เพิกถอน และหน้า Account มีปุ่ม **Revoke all**

## ตรวจที่เดียว ทุกช่องทาง

ทั้งหมดข้างบนแทบไม่มีค่า ถ้าแต่ละช่องทางตรวจคนละแบบ จึงมีที่เดียว Local API ตรวจกฎ access, บทบาท และสิทธิ์ของ key พร้อมกัน และทุกช่องทางที่เหลือเรียก Local API ในนามผู้ใช้

![ทุกช่องทาง ทั้งหน้าแอดมิน REST, Local API ที่ใส่ overrideAccess false, stream แบบ realtime และ MCP ผ่านการตรวจชุดเดียวของ API key บทบาท และกฎ access ซึ่งคืน where สำหรับแถว รายการ field ที่ต้องตัดออก หรือ 404 และ 403](/images/blog/field-level-access/diagram-1.th.png)

- **หน้าแอดมิน** ไม่มีประตูหลัง เป็น client ของ REST API จึงได้เท่ากับที่ REST ให้ผู้ใช้คนนั้นพอดี การซ่อนปุ่มที่บทบาทใช้ไม่ได้เป็นแค่ความสะดวก เซิร์ฟเวอร์เป็นคนตัดสิน
- **REST** ส่งผู้ใช้ที่ login อยู่ หรือเจ้าของ key พร้อม key ไปทุกครั้ง
- **Local API** เชื่อผู้เรียกเป็นค่าเริ่มต้น เพราะเป็นโค้ดเซิร์ฟเวอร์ของคุณเอง ถ้าจะรันในนามผู้ใช้ให้ส่งผู้ใช้ไปด้วย: `cms.find('posts', { user, overrideAccess: false })` นี่เป็นที่เดียวที่กฎต้องเปิดเอง และผมยังลังเลกับมันอยู่ โค้ดที่ seed ข้อมูลหรือรันงานเบื้องหลังต้องทำได้ทุกอย่าง การบังคับให้ทุกจุดส่ง flag จะรกมาก แต่การลืม `overrideAccess: false` ใน route ที่ให้บริการผู้ใช้ก็พลาดง่าย และมีแค่ code review ที่จับได้
- **Realtime** (ตั้งแต่ 1.47.0) ส่งเอกสารให้ผู้ subscribe แต่ละคนแบบที่เขาอ่านผ่าน REST: where รายแถว กฎ read ของ field สิทธิ์ของ key และฉบับร่าง ใช้กับแต่ละคนแยกกัน `where` ที่ใช้ field ที่อ่านไม่ได้ได้ `403` ตอนเปิด stream เหมือน list ทั่วไป เมื่อ session หมดหรือ key ถูกเพิกถอน stream ปิดภายในหนึ่งนาที และ event `leave` กับ `delete` ไปถึงเฉพาะคนที่เคยเห็นเอกสารนั้นก่อนการเปลี่ยน จึงไม่มีใครรู้ id ของบทความที่ไม่เคยมีสิทธิ์อ่าน การตรวจนี้ทำในหน่วยความจำ และเมื่อบอกไม่ได้ (เช่น `like` หรือค่าใน array) จะไม่ส่งอะไรเลย ผลคือ client อาจยังถือเอกสารนั้นไว้จนกว่าจะโหลด list ใหม่ ผมเลือกข้อมูลเก่ากว่าข้อมูลรั่ว
- **MCP** (plugin ยังเป็น experimental) รับเฉพาะ API key tool ถูกสร้างจากสิ่งที่ key อนุญาต และใน collection ที่มีฉบับร่าง `create_` กับ `update_` บันทึกเป็นฉบับร่างเสมอ มีแค่ `publish_` ที่ทำให้ขึ้นเว็บ และต้องเป็น key กับเจ้าของที่มีสิทธิ์เผยแพร่ด้วย

integration test ของเรื่องนี้ (`access.test.ts`, `roles.test.ts`, `owners.test.ts`, `api-keys.test.ts`) รันบน SQLite, PGlite และ Postgres 17 ตัวจริงใน CI ทุก pull request

## สิ่งที่ยังขาด

- **ผู้ใช้หนึ่งคนมีได้บทบาทเดียว** คนที่เป็นทั้งผู้แปลและผู้ตรวจทานต้องมีบทบาทที่ทำไว้สำหรับคู่นั้นโดยเฉพาะ
- **สิทธิ์ของ field มีเฉพาะชั้นบนสุด** field ใน group, array และ blocks ตามตัวแม่ ซ่อนทั้ง group `pricing` จากบทบาทได้ แต่ซ่อน field เดียวข้างในไม่ได้ ถ้าไม่เขียนกฎในโค้ด
- **ยังเปลี่ยนเจ้าของทีละหลายเอกสารไม่ได้** การย้ายบทความร้อยชิ้นจากผู้เขียนคนหนึ่งไปอีกคนเกิดขึ้นตอนลบผู้ใช้ หรือเขียนสคริปต์เอง
- **ค่าเริ่มต้นของ Local API** ยังเชื่อผู้เรียกอย่างที่เล่าไป lint rule หรือ client แบบ "ในนามผู้ใช้" ที่มี type อาจช่วยได้ แต่ยังไม่มีทั้งคู่
- **การอนุมัติ** agent ที่มี key ร่างได้แต่เผยแพร่ไม่ได้ ซึ่งเป็นจุดเริ่มที่ดี แต่ขั้นตอนที่คนอนุมัติการเปลี่ยนของ agent และบันทึกลง audit log อยู่ใน roadmap และยังไม่ได้สร้าง
