ใครเคยติดตั้ง CMS ให้ลูกค้าอาจคุ้นกับภาพนี้ หน้า admin เขียนเป็นภาษาอังกฤษก่อน ส่วนภาษาไทยมักเป็นคำแปลจาก community ที่ตามมาทีหลัง และบางทีก็ตามเวอร์ชันใหม่ไม่ทัน dev อย่างเราใช้ได้ไม่มีปัญหา แต่คนที่ต้องใช้ทุกวันคือแอดมินเว็บของลูกค้า ซึ่งอัปเดตเว็บแทรกระหว่างงานอื่น ทุกปุ่มที่เป็นภาษาอังกฤษคือเวลาที่เขาต้องหยุดคิดอีกนิด

Easy CMS ตั้งใจทำมาให้คนกลุ่มนี้ ในเอกสารออกแบบของโปรเจกต์ ความต้องการของ Editor เขียนไว้บรรทัดเดียวว่า หน้า admin ใช้ง่าย มีภาษาไทย มี draft, preview และประวัติ ส่วน ADR เรื่อง localization ก็เปิดด้วยบริบทเดียวกัน คือลูกค้ากลุ่มหลักของผมทำเว็บไทยที่มักต้องมีภาษาอังกฤษคู่กัน ภาษาไทยจึงเข้ามาตั้งแต่ v0.1 พร้อมภาษาอังกฤษ ไม่เคยอยู่ในรายการ "ไว้ทำทีหลัง"

บทความนี้เล่าว่าต้องทำอะไรบ้าง: ไฟล์ i18n ที่เขียนเองแทน vue-i18n, การแยกภาษาของหน้า admin ออกจากภาษาของเนื้อหา, จุดที่ข้อความภาษาไทยทำให้โค้ดที่คิดแบบภาษาอังกฤษพัง และการดูแล docs สองภาษา ส่วน Easy CMS คืออะไร อ่านได้ใน[บทความแรกของซีรีส์](FIRST_POST_URL)

## i18n ทั้งหมดของ admin อยู่ในไฟล์เดียว

admin เป็น Vue SPA ที่ build มาพร้อม package ข้อความทุกคำอยู่ใน `packages/admin/app/src/lib/i18n.ts` ยาว 1,792 บรรทัด มี 819 key แต่ละ key มีทั้งอังกฤษและไทย ส่วนที่ทำงานจริงมีแค่นี้:

```ts
// packages/admin/app/src/lib/i18n.ts (ตัดมาบางส่วน)
export type Locale = 'en' | 'th'

const en = {
  'nav.create': 'New {name}',
  'list.selected': '{count} selected',
  // … อีก 817 key
} as const

export type MessageKey = keyof typeof en

const th: Record<MessageKey, string> = {
  'nav.create': 'สร้าง{name}',
  'list.selected': 'เลือกแล้ว {count} รายการ',
  // …
}

export function t(key: MessageKey, params: Record<string, string | number> = {}): string {
  const template = messages[locale.value][key] ?? en[key]
  return template.replace(/\{(\w+)\}/g, (_, name: string) => String(params[name] ?? `{${name}}`))
}
```

object ภาษาอังกฤษเป็นต้นฉบับ key ของมันกลายเป็น type และ object ภาษาไทยต้องเป็น `Record` ของ key ชุดนั้นพอดี ถ้าลืมแปลข้อความไหน `vue-tsc` จะ fail ถ้ามี key ภาษาไทยค้างอยู่ทั้งที่ภาษาอังกฤษลบไปแล้วก็ fail เหมือนกัน เพราะ TypeScript ไม่ยอมให้ object literal มี property เกิน และถ้าพิมพ์ `t('nav.creat')` ผิดก็ fail อีก คำถามว่า "แปลครบหรือยัง" จึงได้คำตอบจาก type checker โดยไม่ต้องมีเครื่องมือเพิ่ม และ CI ก็รัน `pnpm typecheck` ทุกครั้ง

ใน dependency ของ admin ไม่มี `vue-i18n` ADR ของ admin บันทึกไว้ว่า "มีพจนานุกรม TH/EN ในตัว" และมีงบขนาดของการโหลดครั้งแรก แต่ไม่ได้เขียนเหตุผลว่าทำไมไม่ใช้ library [TODO: เหตุผลที่เขียน i18n เองแทน vue-i18n ในแบบของคุณ]

สิ่งที่ไฟล์นี้ไม่ได้ทำก็สำคัญพอกัน:

- **ไม่มีกฎพหูพจน์** คำนามไทยไม่เปลี่ยนรูปตามจำนวน เราใช้ลักษณนามแทน เช่น `เลือกแล้ว 3 รายการ` ฝั่งอังกฤษก็ใช้ `(s)` แบบ `{n} field(s)` ไปใน 9 ข้อความ มีแค่สองภาษานี้ ระบบพหูพจน์จึงไม่ได้ช่วยใคร
- **แปลทั้งประโยค ไม่ต่อคำ** ลำดับคำของสองภาษาไม่เหมือนกัน ทุก key จึงเป็น template ทั้งประโยค `New {name}` กลายเป็น `สร้าง{name}` แบบไม่มีเว้นวรรค เพราะภาษาไทยไม่เว้นวรรคระหว่างคำ
- **วันที่ให้ `Intl` ทำ** `formatDate` ใช้ `Intl.DateTimeFormat('th-TH')` ซึ่งใช้ปฏิทินพุทธศักราชให้เอง เวลาเดียวกันแสดงเป็น `21 Oct 2026, 16:30` ในหน้าอังกฤษ และ `21 ต.ค. 2569 16:30` ในหน้าไทย ส่วนนี้ผมไม่ได้เขียนเองเลย

ราคาที่จ่าย: พจนานุกรมทั้งสองภาษาถูกส่งไปให้ทุกคน ใน package 1.13.0 ที่ publish แล้ว ส่วนนี้กินราว 24 KB ของ JavaScript หลัง gzip (ข้อความไทยใน UTF-8 ใช้ 3 bytes ต่อตัวอักษร) สำหรับสองภาษายังรับได้ ถ้าวันหนึ่งมีสิบภาษา ผมจะ lazy-load และถึงตอนนั้น library ก็เริ่มคุ้มแล้ว

## ภาษาของหน้า admin ไม่ใช่ภาษาของเนื้อหา

เรื่องที่ต้องแยกตั้งแต่แรกคือสองอย่างที่ฟังเหมือนเรื่องเดียวกัน: ภาษาของหน้า admin กับภาษาของเนื้อหาที่กำลังแก้

แอดมินคนไทยอาจแปลบทความเป็นภาษาอังกฤษโดยที่หน้า admin ยังเป็นภาษาไทย ส่วนเพื่อนร่วมงานต่างชาติอาจเข้ามาแก้คำผิดในฉบับภาษาไทยโดยใช้หน้า admin ภาษาอังกฤษ admin จึงเก็บค่าสองค่าใน `localStorage` สอง key: `easy-cms-locale` สำหรับหน้า admin และ `easy-cms-content-locale` สำหรับเนื้อหา แม้แต่ component ของ plugin ก็ได้ทั้งสองค่า คือ `uiLocale` สำหรับ label ของตัวเอง และ `locale` สำหรับเนื้อหาที่กำลังแก้

![หน้า admin ภาษาไทยกำลังแก้บทความฉบับภาษาอังกฤษ มีตัวสลับภาษาของเนื้อหาอยู่ด้านบน](/screenshots/translate-th-light.webp)

developer ตั้งภาษาเริ่มต้นของหน้า admin และภาษาของเนื้อหาใน config:

```ts
// easy-cms.config.ts (ตัดมาจาก examples/nuxt-blog)
export default defineConfig({
  admin: { locale: 'th' },
  localization: { locales: ['th', 'en'], defaultLocale: 'th' },
  collections: [
    {
      slug: 'posts',
      fields: [
        { name: 'title', type: 'text', label: { en: 'Title', th: 'ชื่อเรื่อง' }, required: true, localized: true },
        { name: 'cover', type: 'upload', label: { en: 'Cover', th: 'รูปปก' } }, // ใช้ร่วมกันทุกภาษา
      ],
    },
  ],
})
```

ใน snippet นี้มีการแปลสองแบบ `label: { en, th }` แปลหน้า admin คือชื่อ field ที่แอดมินเห็น ส่วน `localized: true` แปลเนื้อหา field จะเก็บค่าแยกต่อภาษาในคอลัมน์ของตัวเอง (`title`, `title__en`) ส่วนรูปและหมวดหมู่มักใช้ร่วมกัน

มีรายละเอียดหนึ่งที่สำคัญ ตอนแอดมินเปิดฉบับภาษาอังกฤษ admin จะขอข้อมูลด้วย `fallbackLocale=false` หน้าเว็บจริงจะ fallback ไปภาษาไทยเมื่อภาษาอังกฤษยังว่าง แต่ฟอร์มแก้ไขต้องเห็นช่องว่างจริงๆ ไม่อย่างนั้นแอดมินจะเห็นข้อความไทยในฟอร์มภาษาอังกฤษ แล้วนึกว่าแปลเสร็จแล้ว

และมีราคาอีกข้อ ถ้า developer ไม่ใส่ `label` admin จะสร้างชื่อจากชื่อ field เอง `publishedAt` จะกลายเป็น "Published at" เป็นภาษาอังกฤษ แม้หน้า admin จะเป็นภาษาไทย อยากให้ชื่อ field เป็นไทย ต้องใส่ label ภาษาไทยใน config

## จุดที่ภาษาไทยทำให้โค้ดแบบภาษาอังกฤษพัง

ส่วนใหญ่แก้ด้วยโค้ดบรรทัดเดียว แต่ทุกข้อพังแบบเงียบๆ ถ้าเราทดสอบแค่ภาษาอังกฤษ

| สมมติฐานแบบอังกฤษ | ภาษาไทยเจออะไร | โค้ดทำอย่างไร |
|---|---|---|
| slug คือ `[a-z0-9-]` | `เริ่มต้นใช้ Easy CMS ใน 5 นาที` เหลือแค่ `easy-cms-5` | `slugify` เก็บตัวอักษร เครื่องหมาย และตัวเลขของทุกภาษา |
| ตัวอักษรคือ `\p{L}` | ไม่มี `\p{M}` สระและวรรณยุกต์หายหมด: `เร-มต-นใช-easy-cms-ใน-5-นาท` | regex คือ `[^\p{L}\p{M}\p{N}]+` |
| ความยาวคือ `string.length` | `ที่นี่` ยาว 6 แต่คนอ่านเห็น 2 ตัว | plugin SEO นับเป็น grapheme ด้วย `Intl.Segmenter` |
| คำแยกกันด้วยช่องว่าง | reading time สั้นเกินจริงมาก | recipe ให้นับตัวอักษร ราว 900 ตัวต่อนาทีสำหรับภาษาไทย |
| ฟอนต์ของระบบก็พอ | ภาษาไทยจะออกมาเป็นฟอนต์ไทยอะไรก็ได้ที่ OS มี | admin มาพร้อมฟอนต์ Anuphan ไฟล์ส่วนภาษาไทย 19 KB |

ภาษาไทยยังซ้อนสระและวรรณยุกต์ไว้บนและล่างตัวอักษร จุดไหนที่ตั้ง `line-height` แน่นๆ ให้ตรวจว่าโดนตัดหรือเปล่า ใน admin ข้อความทั่วไปใช้ 1.55 และหัวข้อใช้ 1.25

มีสองเรื่องที่ยังไม่เสร็จดี เรื่องแรกคือการค้นหา `{ like: '…' }` เป็นการหา substring ธรรมดาแบบไม่สนตัวพิมพ์ ไม่มีการตัดคำไทย บน Postgres มี trigram index (#176) ที่ทำให้ค้นไทยได้เร็ว และมี search adapter (#177) ที่ตัดคำไทยด้วย `Intl.Segmenter` แต่ adapter ที่มีในตัวเก็บ index ไว้ในหน่วยความจำ เว็บใหญ่ยังต้องใช้ search engine ที่ตัดคำไทยได้ เรื่องที่สองคือช่องกรอกวันที่ของเบราว์เซอร์เองไม่สนภาษาของหน้า admin ในภาพด้านบนจะเห็น `08/10/2026` อยู่ข้างๆ `9 ต.ค. 2569`

## docs สองภาษา ที่มี test คุม

เว็บ docs มีหน้า Markdown 74 หน้าใน `website/` และอีก 74 หน้าชุดเดียวกันใน `website/th/` docs สองภาษาจะค่อยๆ ไม่ตรงกันถ้าไม่มีอะไรห้ามไว้ test ของเว็บจึงตรวจว่า:

- ทุกหน้าใน sidebar มีทั้งภาษาอังกฤษและภาษาไทย และทุกรายการใน sidebar มีชื่อทั้งสองภาษา (`sidebar.test.ts`)
- ทุกหน้าใน guide อยู่ใน sidebar ทั้งสองภาษา
- ทุก option ของ config, option ของ field, method ของ Local API และคำสั่ง CLI มีแถวในหน้า reference ทั้งสองภาษา (`reference.test.ts`) test นี้อ่านชื่อ option จาก type ของ core โดยตรง ถ้าเพิ่ม option ใหม่แต่ไม่เขียน docs ภาษาไทย CI จะ fail

ภาพหน้าจอใช้กติกาเดียวกัน `e2e/screenshots.ts` เปิด Nuxt example บน database ชั่วคราว ใส่เนื้อหาตัวอย่างภาษาไทยและอังกฤษ (หมวดหมู่ "คู่มือ", โฟลเดอร์ "แคมเปญ 2026", ไฟล์ "ราคาสินค้า.csv") แล้วถ่ายทุกหน้าทั้งสองภาษาและสองธีม รวม 27 หน้า 108 ภาพ script หาปุ่มจากชื่อที่ screen reader อ่านในแต่ละภาษา ถ้าเปลี่ยน label ภาษาไทยแล้วลืมแก้ script ตัว script จะพัง ไม่ใช่ docs

ADR ทั้ง 56 ฉบับของโปรเจกต์เขียนเป็นภาษาไทย ส่วน issue บน GitHub เขียนเป็นภาษาอังกฤษ [TODO: เหตุผลที่คุณเขียน ADR เป็นภาษาไทย และมันช่วยหรือมีราคาอะไร]

ราคาจริงคือเวลา แก้ docs ทุกครั้งต้องเขียนสองรอบ ข้อความใหม่ใน admin ทุกข้อความต้องมีภาษาไทยก่อน type checker จะยอมให้ผ่าน ผมคิดว่านี่คือจุดที่ควรจ่าย คือจ่ายตอนเขียน ไม่ใช่หลายเดือนต่อมาตอนมีคนมาเจอว่าขาด

## ถ้าคุณทำของให้ตลาดที่ไม่ใช่ภาษาอังกฤษ

- **ใส่ภาษาที่สองตั้งแต่ release แรก** การตามไปครอบ `t()` ให้ข้อความ 800 ข้อความทีหลังยากกว่าเขียนแบบนั้นตั้งแต่ต้องมาก
- **ให้ type checker นับคำแปลให้** `Record<keyof typeof en, string>` ไม่ต้องใช้เครื่องมืออะไรเพิ่ม
- **ใช้ `Intl` ก่อนเขียนเอง** วันที่ ชื่อภาษา (`Intl.DisplayNames` ให้คำว่า "อังกฤษ" สำหรับ `en` ในหน้าไทย) และ grapheme มีให้อยู่แล้ว
- **แยกภาษาของ UI ออกจากภาษาของเนื้อหา** ทั้งใน state, ใน URL และใน API ของ plugin
- **ทดสอบด้วยข้อความจริง** ใส่ข้อมูลตัวอย่างเป็นภาษานั้น ไม่ใช่ lorem ipsum slug ตัวนับ และการค้นหาพังกับข้อความไทยจริง ไม่ใช่กับ "Hello world"

## ข้อจำกัด

หน้า admin มีแค่ภาษาอังกฤษและไทย ถ้าจะเพิ่มภาษาที่สามต้องส่ง pull request แก้ `i18n.ts` ภาษาของเนื้อหาใช้รหัสอะไรก็ได้ แต่ field ที่ localized จะมีคอลัมน์ต่อภาษา จึงเหมาะกับไม่กี่ภาษา (roadmap เขียนไว้ว่าไม่เกินราว 5 ภาษา) ไม่ใช่ 50 ภาษา และอย่างที่บอกไป การค้นหาภาษาไทยด้วย `like` ยังเป็นการหา substring ธรรมดา และ search adapter ที่มีในตัวเก็บ index ไว้ในหน่วยความจำเท่านั้น
