ผมเลื่อนเรื่อง AI ใน [Easy CMS](https://github.com/maritonx/easy-cms) ซึ่งเป็น CMS ที่รันอยู่ในแอป Nuxt หรือ Next.js ของคุณ มานานมาก กล่องแชตที่มุมหน้าแอดมินดูไม่ได้ช่วยใครเท่าไร สิ่งที่ทำให้เปลี่ยนใจคือคำถามที่แคบกว่านั้น: บรรณาธิการปล่อยช่องไหนว่างไว้บ่อยที่สุด คำตอบที่เจอบ่อยคือ alt text ของรูป, คำอธิบายที่ search engine แสดง และภาษาที่สอง

ทั้งสามอย่างเป็นงานเขียนที่ไม่มีใครอยากทำ และทั้งสามมีคำตอบที่ "ถูกพอ" ให้ model ร่างได้ ฟีเจอร์ AI ชุดแรกจึงเป็นสามอย่างนี้พอดี แต่ละตัวเป็นปุ่มข้างช่องที่มันเติมให้ บทความนี้เล่าการตัดสินใจเบื้องหลัง: คุยกับผู้ให้บริการสี่เจ้าโดยไม่ใช้ SDK อย่างไร, ทำไมไม่มี endpoint ที่รับ prompt, คุมค่าใช้จ่ายของทั้งทีมให้คาดเดาได้อย่างไร และแปล rich text อย่างไรไม่ให้ตัวหนาหาย

## กติกาที่ตั้งไว้ก่อนเขียนโค้ด

ผมเขียนข้อเหล่านี้ไว้ก่อน เพราะแต่ละข้อตัดทางที่ง่ายกว่าทิ้งไปหนึ่งทาง:

- **key อยู่บนเซิร์ฟเวอร์เท่านั้น** browser ไม่เรียกผู้ให้บริการเอง key เก็บแบบเข้ารหัสในฐานข้อมูล หรือมาจาก environment ซึ่งชนะเสมอ
- **ไม่มีอะไรบันทึกเอง** คำตอบลงไปในช่อง มีป้ายว่าเขียนโดย AI และมีปุ่ม **เลิกทำ** คนแก้จะบันทึกหรือไม่ก็ได้
- **เลือกผู้ให้บริการเป็นเรื่องของเว็บ** Claude, GPT, Gemini หรือเซิร์ฟเวอร์ของคุณเองอย่าง Ollama ฟีเจอร์ไม่ต้องรู้ว่าใครตอบ
- **ค่าใช้จ่ายมองเห็นได้และจำกัดเป็นรายคน** คนหนึ่งกดปุ่มวนไปเรื่อยๆ ไม่ควรกลายเป็นเรื่องตกใจตอนเห็นบิล
- **ผู้ดูแลต้องยอมรับว่าอะไรถูกส่งออกไป** ตอนเชื่อมผู้ให้บริการ หน้าจอบอกว่าอะไรจะออกจากเซิร์ฟเวอร์ พร้อมลิงก์นโยบายของผู้ให้บริการ และใครกดยอมรับจะถูกบันทึกใน audit log

## ผู้ให้บริการสี่เจ้า ไม่ใช้ SDK

Easy CMS ติดตั้งลงในแอปของคุณ dependency ของมันจึงกลายเป็น dependency ของคุณ SDK สามตัวจะเพิ่มแพ็กเกจหลายตัวให้โปรเจกต์ที่ใช้ผู้ให้บริการแค่เจ้าเดียว หรือไม่ใช้เลย และส่วนของ API ที่ผมต้องใช้ก็มีนิดเดียว: ส่ง system prompt กับข้อความของผู้ใช้ที่มีตัวอักษรและอาจมีรูป แล้วรับข้อความกับจำนวน token กลับมา ผู้ให้บริการแต่ละเจ้าจึงเป็นแค่ `fetch`:

```ts
export interface AiProvider {
  /** integration ที่ connection ของมันใช้ตอบ เช่น `anthropic` */
  readonly integration: string
  readonly generate: (
    values: Readonly<Record<string, string>>, // connection: apiKey, model, baseUrl
    request: AiProviderRequest, // system, prompt, รูป (base64), json, maxTokens, signal
  ) => Promise<{ text: string; usage: { input: number; output: number } }>
}
```

ความต่างของ API ทั้งสามแบบอยู่ในไฟล์เดียวประมาณ 370 บรรทัด:

| | Anthropic | OpenAI และแบบเดียวกัน | Gemini |
|---|---|---|---|
| System prompt | `system` | ข้อความ role `system` | `systemInstruction` |
| รูป | `{ type: 'image', source: { type: 'base64' } }` | URL แบบ `data:` | `inlineData` |
| จำนวน token สูงสุด | `max_tokens` | `max_completion_tokens` ที่ OpenAI, `max_tokens` ที่อื่น | `maxOutputTokens` |
| ตอบเป็น JSON | บอกใน prompt | `response_format: json_object` | `responseMimeType` |

ผู้ให้บริการแบบ OpenAI-compatible ใช้โค้ดเดียวกับ OpenAI แต่มีช่อง **Base URL** เพิ่ม ครอบคลุม Ollama ที่ `localhost:11434/v1`, OpenRouter และเซิร์ฟเวอร์ที่ตั้งเองส่วนใหญ่ มีรายละเอียดหนึ่งข้อ: เซิร์ฟเวอร์บางตัวรับข้อความของผู้ใช้เป็น string ธรรมดาเท่านั้น ไม่รับเป็น list ของ part ข้อความที่ไม่มีรูปจึงส่งเป็น string

การตอบเป็นโครงสร้างคือจุดที่ผู้ให้บริการต่างกันมากที่สุด ผมจึงไม่พึ่งฟีเจอร์ของเจ้าไหนเจ้าเดียว JSON schema จะถูกเขียนเป็นคำพูดใส่ใน system prompt ด้วยเสมอ และถ้า model ห่อคำตอบด้วย code fence ของ Markdown ก็แกะออกก่อน:

```ts
/** ขอ JSON เป็นคำพูดด้วย: ไม่ใช่ทุกเจ้าที่มีโหมด JSON */
function systemOf(req: AiProviderRequest) {
  const json = req.json
    ? `Answer with JSON only, no other text, matching this JSON schema: ${JSON.stringify(req.json)}`
    : undefined
  return [req.system, json].filter(Boolean).join('\n\n') || undefined
}
```

ช่อง model ของผู้ให้บริการแต่ละเจ้ามีปุ่ม **ค้นหา** ที่แสดง model ที่ key นั้นใช้ได้ ไม่มีใครต้องเดาชื่อ model

## ไม่มี endpoint ที่รับ prompt

API ที่คิดได้ทันทีคือ `POST /api/cms/ai` ที่รับ prompt ผมไม่ได้ทำ เพราะถ้ามี ใครก็ตามที่ล็อกอินหน้าแอดมินได้จะได้แชตบอตฟรีที่ใช้ key ของเว็บ และสวิตช์เปิดปิดรายฟีเจอร์ก็ไม่มีความหมาย

แต่ละฟีเจอร์จึงมี endpoint ของตัวเอง (`/admin/ai/alt-text`, `/admin/ai/translate` และอีกตัวใน plugin SEO) และสร้าง prompt บนเซิร์ฟเวอร์จากเอกสาร endpoint ตรวจสิทธิ์แบบเดียวกับ REST API: ขอ alt text ได้เฉพาะไฟล์ที่คุณแก้ได้ และขอแปลได้เฉพาะเอกสารที่คุณแก้ได้ จากนั้นทุกอย่างผ่านฟังก์ชันเดียว:

```ts
const result = await cms.ai?.generate(
  {
    feature: 'summary', // ต้องอยู่ใน aiFeatures และเปิดอยู่
    system: 'You write short, plain excerpts.',
    prompt: `Summarize in one sentence:\n\n${post.text}`,
    images: [{ media: post.cover }],
    json: { type: 'object', properties: { excerpt: { type: 'string' } } },
  },
  { user, about: { collection: 'posts', id: post.id } },
)
```

`cms.ai` เป็น `null` เมื่อไม่ได้ลง plugin คำถาม "ตั้งค่า AI แล้วหรือยัง" ในโค้ดของคุณจึงกลายเป็นเรื่องของ type ภายใน `generate` ทำตามลำดับนี้: ฟีเจอร์ต้องมีอยู่และเปิดอยู่, ผู้ใช้ต้องยังมีโควตาเหลือวันนี้, เลือก connection ของฟีเจอร์นั้น (หรือ connection หลัก), โหลดรูป แล้วจึงถามผู้ให้บริการ ถ้าได้ 429 หรือ 5xx จะลองอีกครั้งหลังรอหนึ่งวินาที และแต่ละคำขอมีเวลา 60 วินาที

401 หรือ 403 แปลว่า key ผิดหรือถูกยกเลิก จึงทำเครื่องหมายที่ connection: หน้าการเชื่อมต่อและ dashboard จะแสดงว่ามีปัญหา และ event `integration.failed` ถูกส่งออกไป ถ้าเว็บลง plugin notify ไว้ด้วย event นี้จะกลายเป็นข้อความ Telegram ถึงคนที่ดูแลเว็บ

## จำกัดเป็นรายคน ไม่ใช่งบ token ของทั้งเว็บ

ความคิดแรกของผมคืองบ token ต่อเดือนของทั้งเว็บ เพราะเป็นตัวเลขที่อยู่บนบิล แต่งบที่ใช้ร่วมกันพังแบบแย่: คนหนึ่งแปลบทความเก่ายาวๆ ในวันจันทร์จนหมด แล้ววันศุกร์ก็ไม่มีใครเขียน alt text ได้

โควตาจึงเป็นต่อคนต่อวัน ค่าเริ่มต้น 100 คำขอ นับจากเที่ยงคืนตามเขตเวลาของเว็บ นับเฉพาะคำขอที่สำเร็จ ผู้ให้บริการล่มจึงไม่กินโควตาของใคร ผู้ดูแลเปลี่ยนตัวเลขได้ในหน้าแอดมิน แต่ละ role มีตัวเลขของตัวเองได้ใน **Settings → Roles** และ 0 แปลว่า role นั้นใช้ AI ไม่ได้เลย

```ts
aiPlugin({ limits: { perUserPerDay: 50, roles: { editor: 20 } } })
```

token ยังแสดงอยู่ แค่ไม่ได้ใช้เป็นตัวจำกัด การ์ดของแต่ละ connection แสดงจำนวนคำขอและ token ของเดือนนี้ และกล่อง AI แยกให้ดูตามผู้ใช้และตามฟีเจอร์ สิ่งที่เก็บไว้คือใครถาม, ฟีเจอร์ไหน, connection ไหน, จำนวน token และเวลา เก็บ 90 วัน ส่วน prompt และคำตอบไม่เก็บ เพราะมันคือเนื้อหาของเว็บ และข้อมูลส่วนบุคคลไม่มีเหตุผลต้องไปอยู่ในตารางการใช้งาน

## Alt text: รูปที่เล็กที่สุดที่ยังใหญ่พอ

ช่อง **ข้อความแทนรูป** ในคลังสื่อมีปุ่ม **เขียนด้วย AI** model ดูรูปแล้วเขียนประโยคเดียว:

```ts
system: [
  'You write alt text for images on a website: one plain sentence saying what the image',
  'shows, for people who cannot see it. Do not start with "Image of" or "Picture of".',
  `At most 125 characters. Write it in ${this.languageOf(options.locale)}.`,
  'Answer with the alt text only, without quotes.',
].join(' '),
```

ภาษามาจาก locale ของเนื้อหาที่กำลังแก้ แปลงเป็นชื่อด้วย `Intl.DisplayNames` ("Thai" ไม่ใช่ "th") ซึ่งชัดกับ model มากกว่ารหัส

การเลือกว่าจะส่งไฟล์ไหนใช้ความคิดมากกว่า prompt ไฟล์ต้นฉบับมักเป็นรูปถ่ายขนาดหลาย MB และผู้ให้บริการนับ token ของรูปตามขนาด Easy CMS ทำสำเนาย่อขนาดไว้อยู่แล้ว จึงส่งสำเนาที่เล็กที่สุดซึ่งกว้างอย่างน้อย 1024 pixel ซึ่งพอสำหรับบรรยายรูป ถ้าไม่มีสำเนาขนาดนั้นจะส่งไฟล์ต้นฉบับ และไฟล์ที่ใหญ่กว่า 4 MB จะถูกปฏิเสธพร้อมคำแนะนำให้เพิ่ม image size ประมาณ 1024 pixel

คำตอบลงไปในช่องพร้อมข้อความ "เขียนโดย AI: ตรวจดูว่าตรงกับรูป" และปุ่ม **เลิกทำ** ช่อง upload ในเอกสารก็บอกด้วยว่ารูปไหนยังไม่มี alt text คลิกแล้วเปิดไฟล์ให้เพิ่มได้ทันที ตัวเตือนนี้อาจสำคัญกว่าปุ่มเสียอีก

## SEO: สองช่อง คำขอเดียว

เมื่อใช้ plugin SEO ตัวอย่างผลค้นหาจะมีปุ่ม **เขียน title และ description ด้วย AI** ทั้งสองช่องมาจากคำขอเดียวที่ตอบเป็น JSON จึงเขียนไปด้วยกันและใช้โควตาของวันแค่ครั้งเดียว ต้นทางคือ title ของเอกสารกับข้อความในช่อง text, textarea และ rich text ระดับบนสุด ตัดที่ประมาณ 6,000 ตัวอักษร collection ที่เนื้อหาหลักอยู่ที่อื่นส่งฟังก์ชัน `aiSource` ของตัวเองได้

plugin รู้ความยาวที่ดีอยู่แล้วเพราะเป็นคนวาดแถบวัดความยาว จึงใส่ตัวเลขนั้นลงใน prompt ถ้าช่องมีข้อความอยู่แล้ว หน้าแอดมินจะถามก่อนเขียนทับ

## แปลแล้วตัวหนายังอยู่

การแปลช่องข้อความธรรมดาคือคำขอเดียว ส่วนที่น่าสนใจคือ rich text เพราะมันเป็น tree ไม่ใช่ string ย่อหน้าอย่าง "ติดตั้ง **Easy CMS** ได้ในห้านาที" คือ text node สามตัว และตัวกลางมี mark ตัวหนา

ผมตัดสองทางที่คิดได้ทันทีทิ้ง ทางแรกคือส่งเป็น HTML หรือ Markdown แล้ว parse คำตอบกลับ ซึ่งใช้ได้จนกว่า model จะ "แก้" tag ให้, ทำลิงก์หาย หรือสลับลำดับรายการ ทางที่สองคือส่ง text node ทีละตัว ซึ่งรักษาโครงสร้างได้แต่แปลเป็นท่อนๆ และ "ได้ในห้านาที" ตัวเดียวก็ขาดประโยคที่มันอยู่

คำขอจึงส่งแต่ละย่อหน้าเป็น list ของชิ้นส่วน แบ่งตรงที่รูปแบบเปลี่ยน แล้วขอให้ตอบกลับมาในรูปร่างเดิม:

![ย่อหน้าภาษาไทยที่มีชื่อเป็นตัวหนาถูกแบ่งเป็นสามชิ้นตรงที่รูปแบบเปลี่ยน แปลทั้งย่อหน้าพร้อมกัน แล้วชิ้นภาษาอังกฤษสามชิ้นกลับไปอยู่ใน text node เดิม ตัวหนาจึงยังอยู่ที่ชื่อ](/images/blog/ai-in-the-admin/diagram-1.th.png)

system prompt ขอให้ model แปลแต่ละย่อหน้าทั้งย่อหน้า แล้วแบ่งคำแปลเป็นจำนวนชิ้นเท่าเดิมในลำดับเดิม ตอนเดินผ่าน tree โค้ดเก็บ setter ของ text node ทุกตัวไว้ การใส่คำตอบกลับจึงเป็นแค่ loop:

```ts
const walk = (node: Node | undefined) => {
  if (!node || typeof node !== 'object') return
  const children = Array.isArray(node.content) ? node.content : []
  const texts = children.filter((c) => c?.type === 'text' && typeof c.text === 'string')
  if (texts.some((c) => c.text!.trim())) {
    paragraphs.push(texts.map((c) => c.text!)) // สิ่งที่ model เห็น
    slots.push(texts.map((c) => ({ set: (t: string) => (c.text = t) }))) // ที่ที่คำแปลจะกลับไป
  }
  for (const child of children) if (child?.type !== 'text') walk(child)
}
```

mark, ลิงก์, รายการ และบล็อกไม่เคยถูกส่งออกไป จึงหายไม่ได้ บล็อกที่อยู่ใน rich text เช่น call-to-action ที่มีหัวข้อ มีช่อง text และ textarea ของตัวเอง ช่องเหล่านั้นถูกส่งไปเป็นย่อหน้าละหนึ่งชิ้น

จากนั้นคำตอบถูกตรวจกับรูปร่างที่ส่งไป: จำนวนย่อหน้าเท่าเดิม แต่ละย่อหน้ามีจำนวนชิ้นเท่าเดิม และเป็น string ทั้งหมด ถ้ามีอะไรไม่ตรง การแปลจะถูกปฏิเสธด้วย "The translation lost its formatting; try again" แทนที่จะใส่ไปครึ่งๆ กลางๆ การตรวจนี้คือสิ่งที่ทำให้โค้ดส่วนที่เหลือเชื่อคำตอบได้

วิธีนี้ไม่สมบูรณ์ เมื่อลำดับคำของสองภาษาต่างกัน model เป็นคนเลือกว่าคำไหนจะอยู่ในชิ้นที่เป็นตัวหนา และอาจไม่ใช่คำที่คุณจะเลือก แต่การย้ายตัวหนาไปหนึ่งคำก็ง่ายกว่าการสร้างย่อหน้าใหม่ทั้งย่อหน้า

ในหน้าแอดมิน ช่องที่มีหลายภาษาเมื่อแก้ใน locale ที่ไม่ใช่ค่าเริ่มต้นจะมีปุ่ม **แปลจาก TH** (หรือภาษาเริ่มต้นของเว็บ) เอกสารที่ยังมีช่องว่างใน locale นี้จะแสดง "ยังมี 3 ช่องที่ยังไม่ได้แปลเป็น EN" เหนือฟอร์ม พร้อมปุ่ม **แปลจาก TH** ที่แปลทั้งหมด ช่องละหนึ่งคำขอ และปุ่ม **เลิกทำ** ปุ่มเดียวสำหรับทุกช่อง การแปลอ่าน locale เริ่มต้นตามที่บันทึกไว้ (รวมฉบับร่างที่รออยู่) ไม่ใช่สิ่งที่ยังพิมพ์ค้างอยู่ในอีกแท็บ

## ทดสอบโดยไม่ต้องมีผู้ให้บริการจริง

end-to-end test เรียก model จริงไม่ได้ เพราะเสียเงินและคำตอบเปลี่ยนทุกครั้ง จึงมี Node server เล็กๆ ทำตัวเป็น API ของ Anthropic บน port ของตัวเอง แอปตัวอย่างชี้ไปที่มันด้วย `ANTHROPIC_API_URL` มันตอบแต่ละฟีเจอร์โดยดูจาก system prompt สำหรับการแปล มันส่งชิ้นส่วนเดิมกลับมาโดยเติม `[EN] ` หน้าชิ้นแรก ซึ่งพิสูจน์ว่ารูปร่างยังอยู่ และทำให้ตรวจผลได้ง่าย:

```ts
const text = JSON.stringify({
  paragraphs: paragraphs.map((p) => p.map((s, i) => (i === 0 ? `[EN] ${s}` : s))),
})
```

test จึงแปลบทความภาษาไทยเป็นภาษาอังกฤษ ทีละช่องแล้วทั้งหมด และตรวจว่าตัวหนายังเป็นตัวหนา

## ถ้าย้อนกลับไปบอกตัวเองตอนเริ่มได้

- **ตัดสินใจก่อน endpoint แรกว่า prompt อยู่ที่ไหน** endpoint ที่รับ prompt อะไรก็ได้เป็นก้าวแรกที่ง่ายที่สุด และเป็นก้าวที่ถอยกลับยากที่สุด
- **จำกัดที่คน ไม่ใช่ที่เว็บ** งบที่ใช้ร่วมกันทำให้ทุกคนรับผลจากบ่ายวันเดียวของคนคนเดียว
- **ส่งโครงสร้างที่ model ทำพังไม่ได้** ส่งชิ้นส่วนไป รับชิ้นส่วนกลับ แล้วตรวจรูปร่าง ดีกว่าการ parse markup ที่ model เขียนใหม่
- **ถือว่า "เขียนโดย AI" เป็นแค่ร่าง** ป้ายกับปุ่มเลิกทำแทบไม่มีต้นทุน แต่ทำให้มีคนอยู่ระหว่าง model กับหน้าเว็บที่เผยแพร่จริงเสมอ

ผู้ให้บริการ AI มาใน Easy CMS 1.33, alt text ใน 1.34 และ SEO กับการแปลใน 1.35 [คู่มือ AI](/th/docs/ai) มีวิธีตั้งค่า ตัวช่วยเขียนใน rich text และข้อความโพสต์ social จะตามมา ถ้าคุณลองกับเว็บจริง โดยเฉพาะเว็บสองภาษา อยากรู้ว่ามันพลาดตรงไหนบ้างใน [กระทู้ feedback](https://github.com/maritonx/easy-cms/issues/137)
