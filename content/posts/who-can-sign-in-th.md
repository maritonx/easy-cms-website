ตั้งแต่ 1.43 ผู้ดูแลเว็บ Easy CMS เปิดผู้ให้บริการเข้าสู่ระบบได้เองในหน้า admin ไม่ว่าจะเป็น Google, Microsoft, GitHub หรือ OpenID Connect เจ้าไหนก็ได้ โดยไม่ต้อง deploy แต่ยังมีอีกสองคำถามที่ค้างอยู่ในโค้ด ใครยังใช้รหัสผ่านได้บ้าง? และใครได้บัญชีแค่เพราะ login ด้วยบัญชี Google หรือ Microsoft ของบริษัท?

สองข้อนี้คือข้อที่เจ็บเวลาตั้งผิด ตั้งแน่นไป องค์กรล็อกตัวเองออกจาก CMS ของตัวเอง ตั้งหลวมไป คนนอกก็สมัครเข้ามาเองได้ 1.46.0 ที่ออกวันที่ 13 พฤศจิกายน 2026 ย้ายทั้งสองข้อมาไว้ที่ **ตั้งค่า → Single sign-on** อยู่ดี บทความนี้เล่าถึงตัวกันพลาดที่ทำให้ผมกล้าทำ และช่องโหว่ที่ยังเหลืออยู่

## กฎในโค้ด

ก่อน 1.46 กฎอยู่ใน `easy-cms.config.ts` และตอนนี้ก็ยังเขียนไว้ที่นั่นได้:

```ts
import { microsoft } from '@easy-cms/auth-oauth'

export default defineConfig({
  serverURL: 'https://cms.example.com',
  auth: {
    providers: [microsoft()],
    // ใครใช้รหัสผ่านได้: true (ทุกคน), false (เฉพาะ admin) หรือบัญชีฉุกเฉิน
    password: { breakGlass: ['emergency@example.com'] },
    // ใครได้บัญชีเมื่อ login ด้วยผู้ให้บริการครั้งแรก
    providerSignUp: { domains: ['example.com'], role: 'editor' },
  },
  // …
})
```

`password` ตั้งได้สามแบบ `true` ให้ทุกคนเข้าได้ทั้งสองทาง `false` ให้ทุกคนใช้ผู้ให้บริการ ยกเว้น admin ที่ยังมีรหัสผ่านไว้เป็นทางเข้าสำรองตอนผู้ให้บริการล่ม ส่วน `{ breakGlass: [...] }` สำหรับองค์กรที่บังคับ MFA ที่ identity provider และไม่อยากให้บัญชีไหน รวมถึง admin เลี่ยงไปใช้รหัสผ่าน จะมีแค่บัญชีในรายชื่อที่ยังใช้รหัสผ่านได้ เก็บไว้ใช้ยามฉุกเฉิน

แบบนี้ดีสำหรับนักพัฒนา แต่ไม่เหมาะกับคนที่ดูแลการเข้าสู่ระบบจริงๆ ในองค์กรส่วนใหญ่ ซึ่งไม่ใช่คน deploy CMS การต้องขอให้นักพัฒนา deploy ใหม่เพื่อให้ฝ่าย IT เปลี่ยนว่าใครใช้รหัสผ่านได้ คือสิ่งที่ [ADR-0066](https://github.com/maritonx/easy-cms/blob/main/docs/adr/0066-admin-overrides-code-defaults.md) ตั้งใจเอาออก: โค้ดเป็นค่าเริ่มต้น และ admin เปลี่ยนได้

## โค้ดยังเป็นค่าเริ่มต้น

[ADR-0068](https://github.com/maritonx/easy-cms/blob/main/docs/adr/0068-sign-in-rules-in-admin.md) ใช้รูปแบบเดียวกันกับกฎสองข้อนี้:

- **ค่าที่ admin ตั้งชนะค่าในโค้ด** กฎแต่ละข้อในแผงบอกว่ามาจากโค้ดหรือถูกเปลี่ยนในหน้านี้
- **บันทึกค่าเท่ากับในโค้ด = ไม่เก็บอะไร** ถ้า admin บันทึกค่าที่ตรงกับ config พอดี ระบบไม่เก็บ การแก้ในโค้ดภายหลังจึงยังมีผล
- **ปุ่ม "ใช้ค่าจากโค้ด"** ลืมค่าที่ admin เปลี่ยนไว้
- **เฉพาะ admin ของทั้งเว็บ** ที่เปลี่ยนกฎได้ API key เปลี่ยนไม่ได้ แม้จะเป็น key ของ admin
- **ทุกเซิร์ฟเวอร์ตามภายใน 30 วินาที** แต่ละเครื่องอ่านกฎใหม่ทุก 30 วินาที การเปลี่ยนจึงไปถึงทุกเครื่องโดยไม่ต้อง restart
- **ทุกการเปลี่ยนลง audit log** เป็น `sign-in.rules` พร้อมค่าก่อนและหลัง

แผงนี้อยู่ใน Single sign-on ซึ่งแสดงกฎเหล่านี้แบบอ่านอย่างเดียวอยู่แล้ว ไม่ได้อยู่ใน Integrations ที่เป็นเรื่องการเชื่อมต่อ หน้าเดียวตอบคำถามว่า "ใครเข้าได้" และตอนนี้เปลี่ยนคำตอบได้ด้วย

## ก่อนบันทึก: กระทบใครบ้าง?

นโยบายรหัสผ่านไม่ใช่การตั้งค่าตามชอบ เปลี่ยนแล้วมีผลทันที บัญชีที่ไม่มีสิทธิ์ใช้รหัสผ่านแล้วจะเสียสิทธิ์ และ session ที่เข้าด้วยรหัสผ่านของบัญชีเหล่านั้นถูกตัด ส่วน session ที่เข้าด้วยผู้ให้บริการยังอยู่ ถ้าไม่ตัด คนที่ login ด้วยรหัสผ่านเมื่อวานจะยังถือ session ที่กฎใหม่บอกว่าไม่ควรมีอยู่

ปุ่มบันทึกจึงอันตราย หน้า admin เลยถามเซิร์ฟเวอร์ก่อน request เดียวกันแต่เติม `?dryRun=1` จะผ่านการตรวจทุกข้อ แล้วตอบว่าการเปลี่ยนนี้จะทำอะไร โดยยังไม่ทำจริง:

```json
{ "passwordLost": 1, "sessionsEnded": 1 }
```

ถ้าตัวเลขไหนมากกว่าศูนย์ หน้า admin ถามก่อนบันทึก: "1 บัญชีจะเข้าสู่ระบบด้วยรหัสผ่านไม่ได้อีก และ 1 session จะถูกตัด บันทึกหรือไม่?" บัญชีที่ไม่มีรหัสผ่านอยู่แล้วไม่ถูกนับว่าเสียสิทธิ์ ส่วน session จากก่อนที่ Easy CMS จะเริ่มบันทึกว่าเข้าด้วยวิธีไหน ถูกนับเป็น session รหัสผ่าน ซึ่งเป็นการเดาที่ปลอดภัยกว่า

## ไม่ยอมให้เปลี่ยนแล้วล็อกคนออก

preview บอกว่าจะเกิดอะไร ส่วนตัวกันตัดสินว่ายอมให้เกิดหรือไม่ ทุกการเปลี่ยนนโยบายรหัสผ่านถูกตรวจด้วยสองคำถาม:

1. **หลังเปลี่ยน ยังมี admin สักคนเข้าได้ไหม?** admin ที่ active นับว่าเข้าได้ถ้านโยบายใหม่ยอมให้ใช้รหัสผ่าน หรือบัญชีผูกกับผู้ให้บริการที่เปิดอยู่ ถ้าก่อนเปลี่ยนมี admin เข้าได้แต่หลังเปลี่ยนไม่มีเลย ระบบไม่ยอมบันทึก: "No admin could sign in after this: an admin needs a password or an account linked to a provider that is on"
2. **คนที่กดบันทึกเองยังเข้าได้ไหม?** ตรวจแบบเดียวกันกับคนที่กดปุ่ม: "You couldn't sign in after this: link a provider on your account page first, or keep yourself on the break-glass list"

ข้อสองคือข้อที่ผมเกือบไม่ได้ใส่ ตัวกันข้อแรกกันไม่ให้เว็บเสีย admin ทุกคน แต่ไม่ได้กัน admin ที่นั่งอยู่หน้าจอตัดทางเข้าของตัวเอง ขณะที่เพื่อนร่วมงานยังเข้าได้ ซึ่งสุดท้ายก็จบที่มีคนถูกล็อกออกและต้องขอความช่วยเหลืออยู่ดี ตัวกันทั้งสองรันบนเซิร์ฟเวอร์ request ที่ส่งมาเองจึงได้คำตอบเดียวกับการกดปุ่ม

## บัญชีฉุกเฉินที่หายไปไม่ได้

ใน config บัญชีฉุกเฉิน (break-glass) เป็นอีเมล ในหน้า admin เลือกจากรายชื่อ admin ที่ active และมีรหัสผ่าน แล้วเก็บเป็น user id เพราะอีเมลเปลี่ยนได้ รายชื่อต้องมี admin อย่างน้อยหนึ่งคน และทุกบัญชีต้อง active และมีรหัสผ่าน ไม่งั้นระบบไม่ยอมบันทึก พร้อมบอกเหตุผล (`… has no password`, `… is deactivated`)

เลือกดีอย่างเดียวไม่พอ เพราะบัญชีเหล่านั้นถูกแก้จากที่อื่นภายหลังได้ ลองนึกภาพว่าผู้ให้บริการล่มทั้งวัน แล้ว admin ฉุกเฉินคนเดียวเพิ่งถูกลด role ไปเมื่อสัปดาห์ก่อนตอนมีคนจัดระเบียบรายชื่อผู้ใช้ ดังนั้นระหว่างที่ใช้รายชื่อบัญชีฉุกเฉินจากหน้า admin admin คนสุดท้ายในรายชื่อที่ยังเข้าด้วยรหัสผ่านได้จะถูกปกป้อง ลบไม่ได้ ปิดไม่ได้ เปลี่ยน role จาก admin ไม่ได้ และเอารหัสผ่านออกไม่ได้ จนกว่าจะมี admin อีกคนในรายชื่อที่มีรหัสผ่าน ข้อความปฏิเสธบอกเหตุผล: "is the last admin who can sign in with a password when the provider is down: add another break-glass account first"

การตรวจนี้อยู่ใน update และ delete ของ Local API ไม่ได้อยู่ในหน้าผู้ใช้ของ admin จึงใช้กับหน้า admin, REST และโค้ดฝั่งเซิร์ฟเวอร์ของคุณเอง แม้จะใส่ `overrideAccess: true`

## สมัครเองตามโดเมนอีเมล โดยมีทางพลาดน้อยลง

กฎข้อที่สองเป็นเรื่องคนใหม่ "ทุกคนที่มีอีเมล `@example.com` ได้บัญชีเป็น editor เมื่อ login ด้วย Google ครั้งแรก" ช่วยประหยัดการส่งคำเชิญได้มาก แต่ก็ห่างจากการเปิดรับทั้งอินเทอร์เน็ตแค่พิมพ์ผิดตัวเดียว

การบันทึกกฎสมัครเองจึงไม่ยอมรับสามอย่าง:

- **โดเมนที่ใครก็สมัครอีเมลได้** `gmail.com`, `outlook.com`, `yahoo.com`, `icloud.com`, `proton.me` และอื่นๆ รวม 21 โดเมนในรายการของ core "ทุกคนจาก gmail.com" แปลว่าทุกคน ข้อความแนะนำให้ส่งคำเชิญแทน
- **role `admin`** admin ต้องถูกสร้างโดย admin ที่ ตั้งค่า → ผู้ใช้ ไม่ใช่สมัครเอง
- **role ที่แก้บัญชีคนอื่นได้** เมื่อเปิดระบบ role ไว้ role ไหนที่สร้าง แก้ หรือลบผู้ใช้ได้จะถูกปฏิเสธด้วย คนที่สมัครเองไม่ควรให้สิทธิ์คนอื่นได้ ถ้าทุก role ทำแบบนั้นได้ แผงจะบอกและลิงก์ไปที่ ตั้งค่า → Roles ให้สร้าง role ที่ทำไม่ได้ก่อน

รายการโดเมนตั้งใจให้สั้น ครอบคลุมความผิดพลาดที่เจอบ่อย ไม่ใช่ผู้ให้บริการอีเมลฟรีทุกเจ้าในโลก และอยู่ใน core ไม่ได้พึ่งแพ็กเกจภายนอก ถ้าโดเมนขององค์กรคุณเป็นโดเมนสาธารณะ คำตอบที่ตรงไปตรงมาคือการเชิญ

ถ้าไม่มีผู้ให้บริการเปิดอยู่ ระบบรับกฎไว้แต่ไม่มีผล และแผงบอกว่า "ตอนนี้ยังไม่มีผล: ไม่มีผู้ให้บริการที่เปิดอยู่"

## config ยังไม่ถูกปฏิเสธแบบเดียวกัน

นี่คือความไม่สม่ำเสมอที่ผมเลือกยอมรับ หน้า admin ปฏิเสธกฎสมัครเองที่ใช้ `gmail.com` หรือ role ที่จัดการผู้ใช้ได้ แต่ `auth.providerSignUp` ใน config ที่ค่าเดียวกันแค่ถูกเตือน ใน log ตอนเซิร์ฟเวอร์เริ่ม และในหน้า Single sign-on

ถ้าทำเป็น error เว็บที่อัปเกรดจาก 1.45 พร้อม config แบบนั้นจะพัง และ Easy CMS สัญญาว่าไม่มี breaking change ใน 1.x จึงเป็นคำเตือนใน 1.x และ ADR บันทึกไว้ว่าจะเป็น error ใน 2.0

## เมื่อโค้ดต้องชนะ: auth.locked

บางทีมไม่อยากให้เปลี่ยนการเข้าสู่ระบบจากหน้า admin ได้เลย เพราะเรื่อง audit หรือเพราะจัดการการเข้าสู่ระบบที่อื่น option ตัวเดียวที่มีมาตั้งแต่ 1.43 สำหรับผู้ให้บริการ ครอบคลุมกฎเหล่านี้ด้วย:

```ts
auth: { providers: [microsoft()], locked: true }
```

เมื่อตั้ง `auth.locked` แผงแสดงกฎพร้อมข้อความ "ตั้งไว้ในโค้ด (auth.locked) เปลี่ยนที่นี่ไม่ได้" เซิร์ฟเวอร์ปฏิเสธการเปลี่ยน และค่าที่ admin เคยเก็บไว้ถูกเมิน

## เมื่อพลาดจริงๆ: easy-cms reset-sign-in

ตัวกันตรวจได้แค่สิ่งที่ฐานข้อมูลรู้ มันไม่รู้ว่า client secret ของ Microsoft หมดอายุไปเมื่อเช้า หรือผู้ให้บริการกำลังล่ม admin ที่ "ผูกกับผู้ให้บริการที่เปิดอยู่" อาจยังเข้าไม่ได้อยู่ดี

สำหรับกรณีนั้นมีคำสั่งที่รันในที่ที่แอปรันอยู่:

```sh
npx easy-cms reset-sign-in
```

คำสั่งนี้ลืมทุกอย่างที่ admin เปลี่ยน ทั้งผู้ให้บริการที่เปิดหรือปิดใน Integrations และกฎใน Single sign-on แล้วกลับไปใช้ค่าใน config มันพิมพ์บอกว่าเปลี่ยนอะไรไป และการ reset ลง audit log คำสั่งนี้ต้องเข้าถึงเซิร์ฟเวอร์ ไม่ใช่หน้า admin ซึ่งตั้งใจ เพราะถ้าคุณ login ไม่ได้ หน้า admin ก็คือสิ่งที่คุณไม่มี

## สิ่งที่ยังขาด

- **"ใช้ค่าจากโค้ด" ไม่มี preview** หน้า admin ถามเซิร์ฟเวอร์ว่ากฎรหัสผ่านใหม่จะทำอะไร แต่การกลับไปใช้ค่าจากโค้ดบันทึกทันที ตัวกันยังทำงาน จึงล็อก admin ทุกคนออกไม่ได้ แต่ตัด session ได้โดยไม่บอกก่อนว่ากี่ session
- **ไม่มีอีเมลถึงคนที่ได้รับผลกระทบ** หน้า login คำเชิญ และ "ลืมรหัสผ่าน" ปรับตามนโยบาย คนจึงรู้ตอนลองเข้า แต่ไม่มีข้อความที่บอกว่า "ตั้งแต่วันนี้ให้เข้าด้วย Microsoft"
- **อีเมลบัญชีฉุกเฉินใน config ไม่ได้รับการปกป้องแบบเดียวกัน** ตัวกัน "admin คนสุดท้ายในรายชื่อ" ใช้กับบัญชีที่เลือกในหน้า admin ส่วนรายชื่อใน config มีแค่คำเตือนใน log เมื่อไม่มีบัญชีในรายชื่อที่มีรหัสผ่าน
- **site members แยกเป็นอีกเรื่อง** การสมัครของผู้เยี่ยมชมเว็บ (`auth.members`) ไม่อยู่ในกฎชุดนี้

## ลองใช้

[คู่มือ Single sign-on](/th/docs/sso#who-can-sign-in) มีทั้งแผงนี้ option ใน config และ `reset-sign-in` เรื่องนี้เป็นส่วนหนึ่งของการทำให้ Easy CMS เป็น backend ที่กฎว่าใครทำอะไรได้อยู่ที่เดียว ([บทความ roadmap](/th/blog/more-than-a-cms-th) เล่าภาพใหญ่ไว้)

ถ้าคุณดูแลการเข้าสู่ระบบให้องค์กร แล้วมีอะไรในนี้ไม่ตรงกับวิธีทำงานของคุณ หรือเคยถูกล็อกออกจาก CMS แบบที่ตัวกันเหล่านี้จับไม่ได้ บอกผมได้ที่ [GitHub discussions](https://github.com/maritonx/easy-cms/discussions)
