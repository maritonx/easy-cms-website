CMS ทำงานเยอะกว่าที่คิดในช่วงที่ไม่มีใครกดอะไรเลย โพสต์ที่ตั้งเวลาไว้ 9:00 ต้อง publish ตอน 9:00 webhook ที่โดน 503 กลับมาต้องส่งใหม่ทีหลัง backup ตอนกลางคืนต้องรัน อีเมลที่ส่งไม่ผ่านต้อง retry

ถ้ามี server ตัวเดียวที่รันค้างไว้ เรื่องนี้ก็แค่ `setInterval` แต่มันเริ่มไม่ง่ายเมื่อแอปเดียวกันรันเป็นสอง instance หลัง load balancer หรือรันบน Vercel ที่ไม่มีอะไรรันค้างไว้ และมี cron มาเรียก endpoint นาทีละครั้ง ตอนนี้สอง process อาจตื่นขึ้นมาพร้อมกันแล้วเห็นเหมือนกันว่า "โพสต์ 42 ถึงเวลาแล้ว" ถ้าทั้งคู่ลงมือ โพสต์จะถูก publish สองรอบ hook `afterChange` รันสองครั้ง และ webhook ยิงออกไปสองครั้ง

ทีมเล็ก ๆ ในไทยหลายทีมเริ่มจาก VPS เครื่องเดียว หรือไม่ก็ deploy บน serverless host ไปเลย พอถึงวันที่ต้องมีงานเบื้องหลังหรือต้องเพิ่ม instance คำถามที่มักตามมาคือ "ต้องเพิ่ม Redis แล้วหรือยัง" บทความนี้เล่าว่า Easy CMS จัดการเรื่องนี้ยังไงโดยไม่เพิ่ม Redis หัวใจของมันคือ `UPDATE` แบบมีเงื่อนไขคำสั่งเดียว และทำงานเหมือนกันทั้งบน Postgres และ SQLite ถ้าคุณกำลังทำแอปของตัวเองที่มีงานเบื้องหลังนิดหน่อย หยิบแพตเทิร์นนี้ไปใช้ได้เลย ([บทความแรกของซีรีส์นี้](FIRST_POST_URL) เล่าว่า Easy CMS คืออะไร)

## บั๊กที่เป็นจุดเริ่มต้น

จนถึงเวอร์ชัน 1.2.0 ตัวรันงาน publish ตามเวลาจะอ่านแถวที่ถึงเวลา ทำงาน แล้วค่อย mark แต่ละแถวว่าเสร็จทีหลัง ระหว่างอ่านกับเขียนไม่มีการล็อกอะไรเลย และการ retry webhook, retry อีเมล กับ backup ก็มีช่องโหว่แบบเดียวกัน เอกสารบันทึกการตัดสินใจของเรื่องนี้ (ADR-0052) เขียนไว้ตรง ๆ ว่าถ้ามีสอง instance ทั้งคู่หยิบงานเดียวกันได้ นี่เป็นบั๊กเรื่องความถูกต้อง ไม่ใช่เรื่องความเร็ว ตัวแก้ขึ้น npm ครั้งแรกในเวอร์ชัน 1.3.0

ทางแก้ที่คนส่วนใหญ่นึกถึงคือคิวจริง ๆ อย่าง BullMQ บน Redis หรือ SQS แต่ Easy CMS เป็น CMS แบบ embedded มันรันอยู่ในแอป Nuxt หรือ Next.js ของคุณ ข้างฐานข้อมูลที่คุณมีอยู่แล้ว queue server คือ infrastructure ชิ้นที่สองที่ต้องรัน ต้อง backup ต้องคอยเฝ้า สำหรับปริมาณงานที่ ADR ประเมินไว้ที่หลักร้อยถึงหลักพันงานต่อชั่วโมง ซึ่ง ADR มองว่า Postgres รับได้สบาย

ถ้าคุณมี VPS เครื่องเดียว Redis คือ service อีกตัวที่ต้องติดตั้งและดูแลบนเครื่องนั้น ถ้าอยู่บน serverless ก็คือบริการอีกเจ้าที่ต้องสมัครและต่อเข้ามา ทั้งสองกรณีเป็นภาระที่ทีมเล็กควรถามก่อนว่าจำเป็นจริงไหม

งานเลยอยู่ในฐานข้อมูลต่อไป pg-boss กับ Graphile Worker ก็สร้างบนแนวคิดเดียวกันนี้สำหรับ Postgres

## หยิบงานก่อน แล้วค่อยทำ

งานเบื้องหลังแต่ละชิ้นคือหนึ่งแถว ก่อนจะทำอะไรกับแถวนั้น instance ต้อง "หยิบ" (claim) มันก่อน ด้วย update ที่จะสำเร็จก็ต่อเมื่อแถวยังหน้าตาเหมือนตอนที่อ่านมา นี่คือ compare-and-set ถ้า instance อื่นหยิบไปก่อน update จะไม่ match แถวไหนเลย แล้ว instance นี้ก็ข้ามไป

database adapter ของ Easy CMS มีเครื่องมือนี้อยู่แล้ว ตั้งแต่ 0.46 `update()` รับ `where` เพิ่มได้ (ไม่บังคับ) และคืน `null` ถ้าแถวที่เก็บอยู่ไม่ตรงเงื่อนไขแล้ว helper สำหรับหยิบงานใน core จึงสั้นมาก:

```ts
// packages/core/src/local-api.ts (ตัดมาบางส่วน)
private async claim(collection, row, changes, expect: Where): Promise<boolean> {
  const { id, ...data } = row
  return (
    (await this.db.update({ collection, id, data: { ...data, ...changes }, where: expect })) !==
    null
  )
}
```

และลูปของงาน publish ตามเวลาก็เรียกใช้แบบนี้:

```ts
// packages/core/src/local-api.ts (runScheduled, ตัดมาบางส่วน)
for (const row of due.docs) {
  const claimed = await this.claim(
    SCHEDULED_JOBS,
    row,
    { state: 'running', updatedAt: now.toISOString() },
    { state: { equals: 'pending' } },
  )
  // process อื่นหยิบไปแล้ว
  if (!claimed) continue
  // ... publish หรือ unpublish แล้วตั้ง state เป็น 'done' หรือ 'failed'
}
```

บน Postgres การหยิบหนึ่งแถวจะออกมาประมาณนี้ (คำสั่งจริงจะเขียนคอลัมน์อื่นของแถวทับด้วย เพราะ `update()` ของ adapter รับทั้ง document)

```sql
UPDATE ecms_scheduled_jobs
SET state = 'running', updated_at = $2
WHERE id = $1 AND state = 'pending'
RETURNING id;
```

![สอง instance อ่านงานที่ pending ตัวเดียวกันและส่ง UPDATE แบบมีเงื่อนไขเหมือนกัน ตัวหนึ่งเปลี่ยนได้หนึ่งแถวแล้วทำงานนั้น อีกตัวเปลี่ยนไม่ได้เลยจึงข้ามไป](/images/blog/postgres-job-queue/diagram-1.th.png)

ทำไมถึงปลอดภัยบนทั้งสองฐานข้อมูล:

- **Postgres** ถ้ามีสอง transaction update แถวเดียวกัน ตัวที่สองจะรอให้ตัวแรก commit ก่อน จากนั้นที่ระดับ `READ COMMITTED` ซึ่งเป็นค่าเริ่มต้น Postgres จะเช็ค `WHERE` ใหม่กับแถวเวอร์ชันล่าสุด ตอนนี้ `state` เป็น `'running'` ไปแล้ว update ตัวที่สองจึงเปลี่ยนศูนย์แถว และ `RETURNING` ไม่คืนอะไรกลับมา
- **SQLite** มีคนเขียนได้ทีละคนอยู่แล้ว `UPDATE` ตัวที่สองจะรันหลังตัวแรก commit และเห็น `'running'` เหมือนกัน

คำสั่งเดียวกัน ได้ผลเหมือนกัน ไม่ต้องมีโค้ดแยกตาม dialect

## ทำไมไม่ใช้ `FOR UPDATE SKIP LOCKED`

ตอนแรกผมตั้งใจจะใช้แบบนั้น issue ที่ติดตามเรื่องนี้ (#153) ยังใช้ชื่อว่า "Claim scheduled jobs and webhook deliveries with `SKIP LOCKED`" อยู่เลย แต่ระหว่างทำผมเปลี่ยนใจ ด้วยเหตุผลสองข้อที่บันทึกไว้ใน ADR

**มันไม่ได้ถูกต้องกว่า** ทั้งสองวิธีให้แต่ละแถวกับคนหยิบแค่คนเดียวเหมือนกัน สิ่งที่ `SKIP LOCKED` เพิ่มมาคือการแย่งกันที่น้อยลง worker จะข้ามแถวที่ transaction อื่นล็อกอยู่ worker สิบตัวจึงได้สิบแถวคนละแถว แทนที่ทุกตัวจะพยายามหยิบแถวแรกพร้อมกัน เรื่องนี้สำคัญเมื่องานมีหลายพันต่อวินาที แต่ถ้ามีสองสาม instance กับงานไม่กี่แถวต่อนาที instance ที่แพ้ก็แค่รัน `UPDATE` ที่ไม่ match อะไร ต้นทุนมีแค่นั้น

**มันจะเปลี่ยน adapter** `SKIP LOCKED` ต้องเพิ่ม method `claim()` ใหม่ใน database adapter ซึ่ง interface นี้ export ออกจาก `@easy-cms/core` และอยู่ในสัญญาความเสถียรของ 1.0 อีกเรื่องคือ SQLite ไม่มี `SELECT ... FOR UPDATE` เลย ยังไงก็ต้องเขียนอีกแบบสำหรับ SQLite อยู่ดี ส่วน `update ... where` ที่มีอยู่แล้วใช้ได้ทั้งสองฐาน

## lease โดยไม่ต้องเพิ่มคอลัมน์

การหยิบงานแก้ปัญหา "สอง instance พร้อมกัน" ได้ แต่ยังไม่แก้ปัญหา "instance หนึ่งหยิบงานไปแล้วตายกลางทาง" (deploy ใหม่, crash, serverless function ชน time limit) แถวนั้นจะค้างอยู่ที่ `running` ตลอดไป

การหยิบงานจึงเป็น lease คือถือสิทธิ์ไว้แบบมีเวลาหมดอายุ การหยิบงาน publish ตามเวลาจะประทับเวลาลง `updatedAt` และทุกรอบที่รันจะเริ่มจากเอาแถวที่ค้าง `running` นานเกิน 10 นาทีกลับคืนคิวก่อน ด้วย compare-and-set แบบเดียวกัน สอง instance จึงคืนแถวเดียวกันซ้ำไม่ได้:

```ts
// packages/core/src/local-api.ts (runScheduled, ตัดมาบางส่วน)
const expired = new Date(now.getTime() - JOB_LEASE).toISOString() // JOB_LEASE = 10 นาที
// ทุกแถวที่เป็น 'running' และ updatedAt < expired:
await this.claim(
  SCHEDULED_JOBS,
  row,
  { state: 'pending', updatedAt: now.toISOString() },
  { and: [{ state: { equals: 'running' } }, { updatedAt: { lt: expired } }] },
)
```

การ retry webhook กับอีเมลมีคอลัมน์ `nextAttemptAt` อยู่แล้ว ตอนหยิบงานจะเลื่อนค่านี้ไปข้างหน้า 5 นาทีก่อนส่ง ถ้าตัวส่งตายไป รายการนั้นก็จะถึงเวลาอีกครั้งเอง ใครเคยใช้ SQS นี่คือแนวคิดเดียวกับ visibility timeout ส่วน backup หยิบด้วยเงื่อนไข `state = 'pending'`

ทั้งหมดนี้ไม่ต้องมี migration เลย lease อยู่ในคอลัมน์ที่แถวมีอยู่แล้ว

## งานของคุณเอง: หนึ่งแถวต่อหนึ่งงาน

แอปและ plugin เพิ่มงานที่รันเป็นรอบของตัวเองได้:

```ts
// easy-cms.config.ts
export default defineConfig({
  // เวลาของวันข้างล่างนี้เป็นเวลาตามเขตนี้ ค่าเริ่มต้น: เขตเวลาของ server (บน serverless มักเป็น UTC)
  timeZone: 'Asia/Bangkok',
  jobs: [
    { name: 'feed:import', every: 600, run: ({ cms }) => importFeed(cms) },
    { name: 'sitemap:refresh', at: '02:00', adminSchedule: true, run: refreshSitemap },
  ],
})
```

`timeZone` ตรงนี้สำคัญกับคนไทยมากกว่าที่เห็น ถ้าไม่ตั้ง `at: '02:00'` จะหมายถึงตีสองตามเขตเวลาของ server ซึ่งบน serverless มักเป็น UTC แปลว่างานจะไปรันตอนเก้าโมงเช้าเวลาไทย พอตั้งเป็น `'Asia/Bangkok'` ตีสองก็คือตีสองจริง ๆ และค่านี้ใช้กับ `backups.at` ด้วย

งานพวกนี้ไม่ใช่แถวในคิว มันคือตารางเวลา ตั้งแต่ 1.3.0 แต่ละงานจะมีหนึ่งแถวในตารางภายในชื่อ `job-runs` ที่มี `name` ไม่ซ้ำกัน (unique) และมี `lastRunAt` ตารางนี้ต้องมี migration แอปที่ใช้ `jobs` ต้องรัน `easy-cms migrate:create` หนึ่งครั้งแล้ว deploy ไปด้วย instance จะหยิบรอบหนึ่งไปได้ด้วยการเลื่อน `lastRunAt` จากค่าที่อ่านมาเป็นเวลาปัจจุบัน:

```ts
// packages/core/src/local-api.ts (runConfigJobs, ตัดมาบางส่วน)
if (!due(row.lastRunAt)) continue
claimed = await this.claim(
  JOB_RUNS,
  row,
  { lastRunAt: stamp, lastStatus: 'running', updatedAt: stamp },
  { lastRunAt: { equals: String(row.lastRunAt) } },
)
```

รอบแรกของงานใหม่จะสร้างแถวแทน และ `name` ที่ห้ามซ้ำก็ทำหน้าที่เป็นการหยิบงานในกรณีนั้น ถ้าสอง instance insert พร้อมกัน จะมี insert หนึ่งที่ล้มเหลว แล้ว instance นั้นก็ข้ามงานนี้ไป

**รอบที่พลาดไปจะรันครั้งเดียว** การเช็คว่าถึงเวลาหรือยังจะเทียบแค่ครั้งล่าสุดที่รันกับเวลาล่าสุดที่งานควรได้รัน ไม่ได้นับว่าพลาดไปกี่รอบ งาน 02:00 ทุกวันบน server ที่ล่มไปสามวัน จะรันหนึ่งครั้งเมื่องานกลับมารัน แล้วกลับไปรันตามรอบปกติ ซึ่งมักเป็นสิ่งที่ต้องการสำหรับงานอย่าง refresh sitemap แต่ผิดสำหรับงานแบบ "ตัดเงินลูกค้าทุกคนวันละครั้ง" งานแบบนั้นควรมีแถวของตัวเองแยกเป็นรายการ

guide ก็บอกตรง ๆ ถึงอีกมุมหนึ่ง: รอบที่หยุดกลางทางจะไม่ถูก retry จนกว่าจะถึงรอบถัดไป ให้เขียนงานให้รันซ้ำสองครั้งแล้วไม่เกิดความเสียหาย

## หยิบงานทางเดียวกัน ไม่ว่าจะเป็น server หรือ cron

งานเบื้องหลังเริ่มได้สามทาง:

| รันอยู่ที่ไหน | อะไรเรียก `runJobs()` |
|---|---|
| server ที่รันค้างไว้ (Nuxt, `easy-cms serve`, Next.js ที่ host เอง) | timer ใน process ทุกนาที |
| serverless (Vercel, Netlify) | cron หรือ scheduled function ที่เรียก `GET <api>/jobs/run` พร้อม `Authorization: Bearer $CRON_SECRET` |
| ที่อื่น ๆ | `npx easy-cms jobs:run` จาก cron ตัวไหนก็ได้ |

```json
// vercel.json — Vercel Cron ส่ง Authorization: Bearer $CRON_SECRET มาให้
{ "crons": [{ "path": "/api/cms/jobs/run", "schedule": "* * * * *" }] }
```

ถ้าคุณอยู่บน VPS เครื่องเดียว ส่วนใหญ่จะตกอยู่ในแถวแรก คือมี server รันค้างไว้และ timer ในตัวจัดการให้ ถ้าอยู่บน serverless ก็คือแถวที่สอง ซึ่งต้องไปตั้ง cron เอง

ทั้งสามทางเรียก `runJobs()` ตัวเดียวกัน จึงผ่านการหยิบงานแบบเดียวกันหมด ภายใน process เดียว `runJobs()` ยังต่อคิวแต่ละรอบไว้หลังรอบก่อนหน้า timer กับ request จาก cron ที่มาพร้อมกันจึงรอกันเอง ส่วนข้าม process ฐานข้อมูลเป็นคนตัดสิน

เทสต์เช็คเรื่องนี้ตรง ๆ: สอง instance บนฐานข้อมูลเดียวกันเรียกตัวรันงานพร้อมกัน แล้วโพสต์ที่ตั้งเวลาไว้ 8 โพสต์ต้อง publish โพสต์ละครั้ง และ hook `afterChange` ถูกเรียกครั้งเดียว อีกเทสต์หนึ่งจำลองงานที่ถูกหยิบไปเมื่อ 11 นาทีก่อน แล้วเช็คว่ามันกลับเข้าคิว CI รันเทสต์ชุดนี้บน SQLite, PGlite และ Postgres 17 ตัวจริง

## ทำให้มองเห็นคิว

คิวที่อยู่ในตารางของคุณเองถูกลืมได้ง่าย และบน serverless ปัญหาที่เจอบ่อยไม่ใช่ race condition แต่เป็น cron ที่ไม่มีใครตั้ง หน้า Settings → Jobs (ในหน้า admin ภาษาไทยคือ ตั้งค่า → งานเบื้องหลัง) มาใน 1.4.0 แสดงตารางเวลาของแต่ละงาน ครั้งล่าสุดที่รัน ใช้เวลาเท่าไร ผลเป็นอย่างไร และจะรันครั้งถัดไปเมื่อไร พร้อมคิวของงาน publish ตามเวลา แอดมินหยุดและกลับมารันงานต่อได้ และเปลี่ยนตารางเวลาของงานที่ตั้ง `adminSchedule` ไว้ได้ ตั้งแต่ 1.4.1 หน้านี้จะเตือนเมื่อไม่มีอะไรรันงานเลยนาน 10 นาที คำเตือนนี้น่าจะจับปัญหาจริงได้มากกว่าโค้ดหยิบงานเสียอีก

## เมื่อไรควรใช้คิวจริง

ดีไซน์นี้เหมาะกับปริมาณงานระดับ CMS แต่ไม่ใช่เครื่องมือที่ถูกถ้าคุณต้องการ:

- **throughput สูง** งานหลายพันต่อวินาที หรือมี worker หลายตัวช่วยกันระบายคิวเดียว กรณีนี้ `SKIP LOCKED` (pg-boss, Graphile Worker) หรือคิวแยกจะคุ้มค่า ผมยังไม่ได้ benchmark ตัวรันงานของ Easy CMS และจะไม่อ้างตัวเลขใด ๆ
- **latency ต่ำ** งานถูกหยิบด้วยการ polling: นาทีละครั้งบน server หรือถี่เท่าที่ cron ของคุณเรียก (guide ของ Netlify ใช้ทุกห้านาที) ไม่มีการ push งานมาหา
- **priority และ rate limit** ADR-0052 ระบุว่ายังไม่ได้ทำทั้งสองอย่าง
- **งานที่ยาวหรือต้องรันขนานกัน** รอบหนึ่งทำงานตามลำดับ งานที่ช้าจะทำให้งานถัดไปช้าตาม lease 10 นาทีก็ตั้งอยู่บนสมมติฐานว่า publish หนึ่งครั้งไม่มีทางนานขนาดนั้น
- **คิวที่ใช้ร่วมกันหลาย service** ถ้ามีหลายแอปที่ทั้งสร้างและรับงาน คิวนั้นไม่ควรเป็นส่วนหนึ่งของฐานข้อมูลของแอปใดแอปหนึ่ง

## บทเรียนสำหรับแอปของคุณ

ถ้างานเบื้องหลังของคุณมีไม่เกินหลักร้อยแถวต่อชั่วโมง คุณน่าจะยังไม่ต้องมี queue server สิ่งที่ต้องมีคือสามอย่าง:

1. **หนึ่งแถวต่องานหนึ่งชิ้น** ที่มี state หรือ timestamp ไว้เทียบได้
2. **การหยิบงานที่เป็น `UPDATE` แบบมีเงื่อนไขคำสั่งเดียว** โดยถือว่า "เปลี่ยนศูนย์แถว" แปลว่ามีคนอื่นหยิบไปแล้ว ฐานข้อมูลไหนที่มี transaction ก็ทำได้ ใช้ผ่าน ORM ก็ได้
3. **lease** เพื่อให้งานที่ถูกหยิบโดย process ที่ตายไปแล้วกลับเข้าคิวหลังหมดเวลา

แล้วทำให้มันมองเห็นได้ เพราะบั๊กที่คุณจะเจอจริง ๆ คือ cron ที่ไม่เคยรัน
