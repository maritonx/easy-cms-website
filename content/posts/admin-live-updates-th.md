ก่อน Easy CMS 1.48.0 ที่ออกเมื่อ 14 พฤศจิกายน 2026 หน้าแอดมินมีวิธีทำงานหายแบบเงียบๆ อยู่หนึ่งทาง สองคนเปิดบทความเดียวกัน ทั้งคู่แก้ คนที่บันทึกทีหลังทับของคนแรก และไม่มีใครรู้ หน้ารายการก็มีปัญหาเดียวกันในแบบที่เบากว่า: แสดงสิ่งที่มีอยู่ตอนเปิด จนกว่าจะโหลดใหม่

stream realtime จาก 1.47.0 ([บทความก่อนหน้า](/th/blog/realtime-sse-th) เล่าว่ามันทำงานอย่างไร) ทำให้หน้าแอดมินได้ยินการบันทึกจากที่อื่น พอเอามาใช้จริง งานส่วนใหญ่กลับไปอยู่ที่คำถามเดียวที่ผมไม่คิดว่าจะยาก: เมื่อ event ของเอกสารที่เปิดอยู่มาถึง การบันทึกนั้นเป็นของเราเองหรือเปล่า

## อะไรเปลี่ยนสำหรับ editor

collection ที่มี `realtime: true` (ตอนนี้ schema ของแอดมินบอกว่าตัวไหนมี) จะสดสามที่ ส่วน collection อื่นทำงานเหมือนเดิมและไม่เปิด connection

- **หน้ารายการ** มีจุด "สด" ข้างหัวรายการ เป็นสีเทาพร้อม "กำลังเชื่อมต่อใหม่…" ตอน stream หลุด แถวที่แสดงอยู่เปลี่ยนในที่เมื่อถูกบันทึกจากที่อื่น แถวที่ถูกลบจากที่อื่นจางลงพร้อมป้าย "ลบแล้ว" ส่วนเอกสารใหม่และเอกสารที่เข้าหรือออกจากสิ่งที่รายการแสดง ถูกนับไว้ในปุ่ม "มีการเปลี่ยนแปลง 3 รายการ · แสดง" แทนที่จะโผล่หรือหายไปเอง
- **หน้าแก้ไขและ drawer** ถ้าไม่มีอะไรค้างบันทึก การบันทึกจากที่อื่นจะโหลดเอง พร้อมข้อความเล็กๆ "อัปเดตจากการบันทึกล่าสุดแล้ว" ถ้ามีสิ่งที่ยังไม่บันทึก แถบจะขึ้นว่า "เอกสารนี้ถูกบันทึกจากที่อื่น" พร้อม **โหลดฉบับใหม่ (ทิ้งของฉัน)** และ **ใช้ของฉัน** ถ้าเลือกใช้ของตัวเอง ตอนบันทึกจะถามก่อนว่า "เอกสารนี้ถูกบันทึกจากที่อื่นหลังจากคุณเปิด ต้องการบันทึกของคุณทับฉบับนั้นหรือไม่"
- **ถูกลบ หรือไม่มีสิทธิ์ดูแล้ว** แถบบอก "เอกสารนี้ถูกลบแล้ว" หรือ "คุณไม่สามารถดูเอกสารนี้ได้อีกต่อไป" และปิดปุ่มบันทึก สิ่งที่พิมพ์ไว้ยังอยู่ในหน้าให้คัดลอก หน้าไม่ redirect พาคุณออกจากข้อความของตัวเอง

ตั้งใจไม่บอกว่า*ใคร*บันทึก event ไม่มีข้อมูลผู้เขียน และ "ที่อื่น" รวมถึงตัวคุณเองในอีกแท็บด้วย

## ทำไม updatedAt จำการบันทึกของหน้าตัวเองไม่ได้

หน้าแก้ไข subscribe เอกสารของตัวเอง เมื่อคุณกดบันทึก เซิร์ฟเวอร์เขียนเอกสาร เขียนแถว event แล้ว stream ก็ส่ง `update` ของเอกสารเดียวกันนั้นกลับมาที่หน้าเดิมในอีกครู่ ถ้าหน้าทำกับมันเหมือนการบันทึกอื่น ทุกครั้งที่บันทึกจะขึ้น "อัปเดตจากการบันทึกล่าสุดแล้ว" หรือแย่กว่านั้น ถ้าคุณเริ่มพิมพ์ต่อทันทีหลังบันทึก จะขึ้น "เอกสารนี้ถูกบันทึกจากที่อื่น" กับงานของตัวเอง

ไอเดียแรกชัดเจน: response ของการบันทึกมี `updatedAt` เมื่อ event มา ก็อ่านเอกสาร ถ้า `updatedAt` ตรงกับที่การบันทึกตอบมา ก็คือของเรา

ใช้ได้จนกระทั่งเจอฉบับร่าง เมื่อบันทึกฉบับร่างของเอกสารที่ publish อยู่แล้ว แถวที่ publish อยู่ไม่เปลี่ยน และฉบับร่างถูกเก็บเป็น version ซึ่งเขียนหลังแถวเอกสาร `updatedAt` ที่แอดมินอ่านกลับมาสำหรับฉบับร่างนั้นจึงไม่ใช่ค่าที่การบันทึกตอบมา การจับคู่จึงล้มเหลวพอดีกับเอกสารที่สอง editor มีโอกาสชนกันมากที่สุด: หน้าที่ publish อยู่แล้วกำลังถูกปรับในฉบับร่าง

ผมอาจพยายามทำให้เวลาสองค่านี้ตรงกัน แต่นั่นจะทำให้กฎเรื่องความถูกต้องไปพึ่งลำดับของการเขียนสองครั้งข้างในการบันทึก หน้าจึงแยกการบันทึกของตัวเองด้วย**เนื้อหา**แทน:

1. ระหว่างที่หน้ากำลังยุ่ง (บันทึก โหลด ลบ หรือรัน action) event ที่เข้ามาจะรอ เก็บไว้แค่ตัวล่าสุด เพราะพอแล้ว
2. เมื่อหน้าว่าง ก็อ่านเอกสารใหม่ แบบเดียวกับที่หน้าอ่าน
3. แปลงเป็นค่าในฟอร์ม แล้วเทียบกับ **baseline** ของฟอร์ม: snapshot ของสิ่งที่โหลดหรือบันทึกล่าสุด ซึ่งการบันทึกเพิ่งตั้งไว้
4. เท่ากัน แปลว่าเป็นการบันทึกของหน้านี้เอง หรือไม่มีอะไรที่มองเห็นเปลี่ยน ไม่ต้องทำอะไร
5. ต่างกันและฟอร์มไม่มีอะไรค้าง: โหลดใหม่ แสดง "อัปเดตจากการบันทึกล่าสุดแล้ว" ต่างกันและฟอร์มมีสิ่งที่ยังไม่บันทึก: แสดงแถบ conflict

`updatedAt` ยังมีหน้าที่ แค่เล็กลง: event ที่เอกสารเก่ากว่าหรือเท่ากับที่หน้ามีอยู่ถูกข้ามไปเลยโดยไม่ต้องอ่านอะไร

ราคาคือการอ่านเอกสารเพิ่มหนึ่งครั้งต่อการเปลี่ยนแปลงที่หน้าแก้ไขเห็น สิ่งที่ได้คือคำถาม "ของเราไหม" ถูกตอบด้วยสิ่งเดียวกับที่ editor สนใจ: สิ่งที่อยู่บนเซิร์ฟเวอร์ต่างจากที่เราคิดว่าบันทึกไปหรือเปล่า

## รายการที่ไม่ขยับใต้เคอร์เซอร์

หน้ารายการคือส่วนที่มีเรื่อง UX ให้ตัดสินใจมากที่สุด และส่วนใหญ่มาจากกฎข้อเดียว: **ห้ามขยับแถวที่ผู้ใช้อาจกำลังจะคลิก**

![รายการในหน้าแอดมินทำอะไรกับการเปลี่ยนแปลงสดแต่ละแบบ: แถวที่แสดงอยู่ถูกอ่านใหม่และเปลี่ยนในที่ แถวที่ถูกลบจากที่อื่นจางลง และอะไรก็ตามที่จะเพิ่ม ย้าย หรือเอาแถวออกถูกนับไว้ในปุ่ม "มีการเปลี่ยนแปลง N รายการ · แสดง"](/images/blog/admin-live-updates/diagram-1.th.png)

ตรรกะอยู่ในฟังก์ชันเล็กๆ ชื่อ `listReaction` ที่มีคำตอบสี่แบบ:

- **แถวที่แสดงถูก update หรือ publish:** `refresh` รายการอ่านแถวเหล่านั้นใหม่แบบเดียวกับที่รายการอ่าน แล้วสลับเข้าที่เดิม การเปลี่ยนแปลงที่มาติดๆ กันถูกรวมด้วย timer 100 ms
- **แถวที่แสดงถูกลบ:** `deleted` อยู่ที่เดิม จางลง มีป้าย "ลบแล้ว" และ checkbox ถูกปิด ถ้าเลือกไว้ก็ถูกเอาออกจากที่เลือก
- **อะไรก็ตามที่จะเพิ่ม ย้าย หรือเอาแถวออก:** `pending` เอกสารใหม่, แถวที่แสดงแต่ไม่ตรงตัวกรองแล้ว, เอกสารที่อื่นที่ตอนนี้ตรงตัวกรอง ถูกนับไว้ กด **แสดง** แล้วรายการโหลดใหม่ด้วยหน้า การเรียง ตัวกรอง และแถวที่เลือกไว้เดิม
- **ไม่ได้แสดงอยู่ และถูกลบหรือออกไปอยู่แล้ว:** `ignore`

เมื่อรายการมีตัวกรอง คำถาม "การเปลี่ยนนี้อยู่ในรายการของเราไหม" เป็นสิ่งที่ฝั่ง client ตอบเองไม่ได้ รายการจึงถาม API: ใช้ `where` ของรายการเอง บวก `id in (…)` ของเอกสารที่เปลี่ยน แล้วเทียบกับสิ่งที่แสดงอยู่ นับเฉพาะเอกสารที่การอยู่ในรายการเปลี่ยนจริง

ถ้า stream ต่อจากเดิมไม่ได้ (`reset`) รายการไม่รู้ว่าพลาดไปกี่อย่าง ปุ่มจึงขึ้นแค่ "มีการเปลี่ยนแปลง · แสดง"

### ทำไมรายการตามทั้ง collection

ทางที่ดูชัดที่สุดคือ subscribe ด้วยตัวกรองของรายการ ให้เซิร์ฟเวอร์ส่งเฉพาะที่ตรง ผมไม่ทำ เพราะเรื่องที่เขียนไว้ในบทความ realtime: `leave` และ `delete` ไปถึงเฉพาะคนที่เคยเห็นเอกสารมาก่อน และการตรวจนั้นรันในหน่วยความจำ `like` ซึ่งเป็นสิ่งที่ช่องค้นหาของแอดมินใช้ เป็นหนึ่งในสิ่งที่มันตัดสินไม่ได้ จึงนับว่ามองไม่เห็น รายการที่ subscribe ด้วยคำค้นจะไม่มีวันได้ยินว่าแถวที่แสดงอยู่ถูกลบ

รายการจึงตามทั้ง collection แล้วตัดสินว่าอะไรอยู่ในรายการด้วยการถาม API ราคาเขียนไว้ใน ADR: collection ที่ถูกแก้บ่อยมาก รายการที่กรองแคบๆ ก็ยังได้ทุก event end-to-end test บังเอิญเริ่มจากการค้นหา (`?q=Live`) ซึ่งก็คือกรณีที่การออกแบบนี้ป้องกันไว้

## stream เดียวต่อแท็บ

แท็บแอดมินหนึ่งแท็บอาจเปิดรายการไว้และมี drawer ของเอกสารซ้อนอยู่ข้างบน และผู้ใช้เปลี่ยนหน้าได้เร็ว ถ้าทุกมุมมองเปิด stream ของตัวเอง คนเดียวที่เปิดไม่กี่แท็บก็ชนขีดจำกัด 10 stream ต่อผู้ใช้ของเซิร์ฟเวอร์ได้ไม่ยาก

ทุกมุมมองในแท็บจึงใช้ stream เดียวกัน (`lib/realtime.ts`) แต่ละมุมมองลงทะเบียนสิ่งที่ตาม คือ collection หรือเอกสารเดียว มุมมองที่ตามสิ่งเดียวกันใช้ subscription ร่วมกันบน stream

protocol ของ 1.47 ไม่ให้ stream เปลี่ยน subscription เมื่อมุมมองเปิดหรือปิด แอดมินจึงรอ **100 ms** เพื่อให้การเปลี่ยนหน้า ซึ่งเอา subscription หนึ่งออกและเพิ่มอีกอันเข้า เปิด stream ใหม่แค่ตัวเดียวไม่ใช่สองตัว แล้วเปิด stream ใหม่ด้วยชุดใหม่ เริ่มจากจุดที่ stream เดิมไปถึง เพื่อการนี้ client ของ core ได้ตัวเลือกเพิ่มหนึ่งตัวใน 1.48.0:

```ts
const next = cms.subscribe(newSubscriptions, handlers, { lastEventId: stream.lastEventId })
stream.close()
```

`lastEventId` คือจุดที่ stream ไปถึง: id ของ event ล่าสุด หรือตำแหน่งที่ `ready` หรือ heartbeat บอกมา stream ใหม่ replay สิ่งที่มาหลังจากนั้น จึงไม่พลาดอะไรระหว่าง stream สองตัว

การ replay นี้มีผลข้างเคียงที่รายการต้องจัดการ มุมมองที่เพิ่ง subscribe อาจได้ event จากก่อนที่มันโหลด ซึ่งถูก replay มาเพราะ *stream* เริ่มจากตำแหน่งที่เก่ากว่า stream ที่ใช้ร่วมกันจึงติดป้าย event ที่มาก่อน `ready` ครั้งแรกของ subscription ว่าเป็น replay และรายการไม่นับมันเป็นการเปลี่ยนแปลงใหม่ แต่แถวที่แสดงอยู่ยังถูกอ่านใหม่ เพราะอ่านซ้ำไม่เสียหายอะไร

เมื่อเป็น stream เดียวต่อแท็บ `maxPerUser` ค่าเริ่มต้น 10 จึงเท่ากับประมาณสิบแท็บแอดมินต่อผู้ใช้ต่อเซิร์ฟเวอร์ คู่มือเขียนไว้แล้ว

## ส่วนที่มองไม่เห็นในภาพหน้าจอ

- แถบและข้อความ "อัปเดต" อยู่ใน `aria-live="polite"` โปรแกรมอ่านหน้าจออ่านให้ฟังโดยไม่ย้าย focus ออกจากช่องที่กำลังพิมพ์
- จุดสดหยุดกะพริบเมื่อเปิด `prefers-reduced-motion`
- ไม่มี toast ตอน stream หลุด สัญญาณเดียวคือจุดสีเทาที่มี tooltip "กำลังเชื่อมต่อใหม่…"
- ข้อความทุกตัวมีทั้งภาษาอังกฤษและไทย เหมือนส่วนอื่นของแอดมิน

end-to-end test รันเรื่องนี้เป็นแอดมินสองคนในหน้าต่างเบราว์เซอร์สองบาน บนตัวอย่าง Next.js: A เปลี่ยนชื่อบทความ แถวในรายการของ B เปลี่ยนตาม A สร้างฉบับร่างในอีกแท็บ B เห็น "1 change" ไม่ใช่แถวใหม่ จนกว่าจะกด Show A ลบมัน แถวของ B จางลง B เปิดบทความ การบันทึกของ A โหลดเข้ามาเงียบๆ แล้วทั้งคู่แก้ B เลือกใช้ของตัวเอง ถูกถามก่อนบันทึกทับ ส่วน A ที่ไม่มีอะไรค้างบันทึกก็เห็นฉบับของ B เข้ามา สุดท้าย A ลบบทความระหว่างที่ B พิมพ์อยู่ ข้อความของ B ยังอยู่แต่ปุ่ม Publish ถูกปิด

## สิ่งที่ยังขาด

- **การตรวจการบันทึกที่ล้าสมัยฝั่งเซิร์ฟเวอร์** การบันทึกสองที่ในเวลาเดียวกันพอดียังทับกันได้ เพราะเซิร์ฟเวอร์ยังไม่ปฏิเสธการบันทึกที่ทำจากฉบับเก่า แอดมินทำให้ช่องนี้แคบลงเหลือแค่ชั่วขณะ แต่ที่จะปิดได้จริงคือเซิร์ฟเวอร์ที่ตอบ `409` เมื่อการบันทึกมาจาก version เก่า ซึ่งวางแผนไว้แต่ยังไม่ได้ทำ
- **presence และการล็อก** ยังไม่บอกว่าใครเปิดเอกสารเดียวกันอยู่ ไม่อยู่ในขอบเขตของรอบนี้
- **ใครเป็นคนบันทึก** event ไม่มีข้อมูลนี้ แถบจึงบอกไม่ได้
- **ค่าใช้จ่ายบน collection ที่แก้บ่อย** แต่ละการเปลี่ยนที่หน้าแก้ไขเห็นอ่านเอกสารหนึ่งครั้ง แต่ละการเปลี่ยนในรายการอ่านแถวที่เปลี่ยน และถาม API เรื่องการอยู่ในรายการเมื่อมีตัวกรอง

## ลองใช้

ถ้า collection ของคุณมี `realtime: true` อยู่แล้ว อัปเดตเป็น 1.48.0 แล้วหน้าแอดมินจะสดเลย ไม่ต้องเปิดอะไรเพิ่ม [หัวข้อ "ในหน้า admin" ของคู่มือ realtime](/th/docs/realtime#in-the-admin) อธิบายแต่ละสถานะ และ [ADR-0071](https://github.com/maritonx/easy-cms/blob/main/docs/adr/0071-admin-live-updates.md) มีเหตุผลเบื้องหลัง ถ้า editor ของคุณเจอกรณีที่แอดมินเดาผิดว่าการบันทึกเป็นของใคร อยากให้เล่าไว้ใน [GitHub discussions](https://github.com/maritonx/easy-cms/discussions)
