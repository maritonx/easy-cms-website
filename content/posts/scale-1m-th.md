Easy CMS คือ headless CMS ที่รันอยู่ในแอป Nuxt หรือ Next.js ของคุณ บน Postgres หรือ SQLite ของคุณเอง หลังออก 1.0 คำถามที่ผมได้ยินจากทีมต่างๆ บ่อยที่สุดคือคำถามที่ตรงไปตรงมาที่สุด: ถ้าเนื้อหาเยอะขึ้นมาก มันยังไหวไหม

ผมจึงวัดก่อนแก้อะไรทั้งนั้น บทความนี้เล่าว่าล้านเอกสารสอนอะไรผมบ้าง: ตัวเลข การแก้สี่อย่าง สิ่งที่ตั้งใจไม่เพิ่ม และสิ่งที่ยังช้าอยู่

## การทดสอบ

workflow ของ GitHub Actions รันทุกคืนตอนตีสามเวลากรุงเทพ:

- Postgres 17 ใน Docker บน runner 4 core โดยมี `easy-cms serve` อยู่ข้างหน้า
- **บทความ 1,000,000 รายการ** เขียนผ่าน Local API แบบที่แอปจริงเขียน: เนื้อหาภาษาไทยพร้อมชื่อภาษาอังกฤษ มีฉบับร่างและเวอร์ชัน หมวดหมู่ แท็ก และบล็อก
- **editor 200 คน** พร้อมกันห้านาที: อ่าน 90% บันทึก 10%
- อีกรอบแยกต่างหาก ส่ง request พร้อมกัน 20 ตัวต่อชนิด เพื่อดูแต่ละชนิดแยกกัน

workflow จะล้มเมื่อ request ชนิดใดช้ากว่าค่ามัธยฐานของเจ็ดคืนล่าสุดเกิน 20% (p95) ส่วนเป้า 200 ms ในเอกสาร requirement รายงานไว้แต่ไม่บังคับ เพราะเป้าที่โค้ดยังทำไม่ได้จะทำให้ workflow แดงทุกคืนเปล่าๆ

บทเรียนแรกมาก่อนตัวเลขใดๆ ที่ล้านแถว Postgres เริ่มตอบ 500 พร้อมข้อความ "could not resize shared memory segment" เพราะ query แบบขนานใช้หน่วยความจำร่วมผ่าน `/dev/shm` และ Docker ให้ container แค่ 64 MB เป็นค่าเริ่มต้น แก้ด้วย `--shm-size=1g` ถ้าคุณรัน Postgres ใน Docker กับตารางใหญ่ ลองเช็กค่านี้ดู

## อะไรที่เร็วตั้งแต่แรก

การอ่านตาม id หรือ slug และหน้าแรกของ list ทำได้ดีตั้งแต่ล้านแถว เพราะ index ก็คือ index รอบแรกยังเผยปัญหาทั้งหมดในโหลดผสม: การอ่านตอนมี editor 200 คนมี p95 ราว 30 วินาที

ไม่มีอะไรพัง แค่ request ช้าๆ ไม่กี่ชนิดถือ connection ของ Postgres ไว้นานจน request อื่นทุกตัวต้องรอ query ช้าตัวเดียวทำให้ทุกอย่างช้า

## แก้ที่ 1: เลิกนับทุกหน้า (1.8)

list ที่แบ่งหน้าทุกตัวคืน `totalDocs` และ `totalPages` ทุกหน้าจึงรัน `count(*)` กับผลทั้งหมด ที่ล้านแถว การนับนี้คือส่วนที่แพงที่สุดของ request แบบ list ส่วนใหญ่

แก้สองอย่าง:

- `count: false` (REST `?count=false`) ข้ามการนับ แล้วดู `hasNextPage` จากการดึงเกินมาหนึ่งแถว หน้า archive และ infinite scroll ไม่ต้องใช้ยอดรวม
- ยอดนับของ list เดียวกันถูกใช้ซ้ำภายใน `countCacheSeconds` ค่าเริ่มต้น 5 วินาที เอกสารยังเป็นปัจจุบันเสมอ มีแค่ยอดรวมที่อาจเก่าได้เท่านั้น list ที่ editor ห้าสิบคนเปิดอยู่จึงนับครั้งเดียวในช่วงนั้น ไม่ใช่ห้าสิบครั้ง

## แก้ที่ 2: cursor สำหรับหน้าลึกๆ (1.9)

`OFFSET 500000` ทำให้ Postgres อ่านแล้วทิ้งไปห้าแสนแถว ทางแก้เป็นวิธีเก่าที่รู้กันดี: จำว่าหน้าก่อนจบที่ไหน แล้วต่อจากตรงนั้น

```ts
const page = await cms.find('posts', { cursor: '', limit: 20 })
const next = await cms.find('posts', { cursor: page.nextCursor, limit: 20 })
```

cursor เก็บค่าที่ใช้เรียงของแถวสุดท้าย และผูกกับ query ของมัน: `where`, `sort` และ locale ต้องเหมือนเดิม ไม่อย่างนั้นจะถูกปฏิเสธ หน้าถัดไปด้วย cursor ลึกเข้าไปใน list ได้ p95 29 ms ส่วนการเปิดหน้าตามเลขหน้าลึกๆ แบบสุ่มยังเป็น 5.6 วินาที และ 5.9 วินาทีเมื่อไม่นับยอดรวม ซึ่งยืนยันว่าเวลาหมดไปกับการข้ามแถว ไม่ใช่การนับ

หน้า admin ยังมีเลขหน้าเพราะ editor ใช้ ส่วน API client มี `maxPage` จำกัดว่าเปิดหน้าตามเลขลึกได้แค่ไหน แล้วแนะนำให้ใช้ `cursor` แทน

## แก้ที่ 3: ค้นภาษาไทยโดยไม่ต้องอ่านทุกแถว (1.10)

ภาษาไทยเขียนติดกันไม่เว้นวรรคระหว่างคำ การค้นส่วนหนึ่งของชื่อเรื่องจึงเป็น `like '%…%'` และ b-tree index ช่วย pattern ที่ขึ้นต้นด้วย `%` ไม่ได้

แต่ trigram index ช่วยได้ `index: 'trigram'` บน field ข้อความจะสร้าง GIN index แบบ `pg_trgm` และ Postgres ใช้มันกับ `like` ที่หาส่วนใดก็ได้ของข้อความ

```ts
{ name: 'title', type: 'text', localized: true, index: 'trigram' }
```

ตอนนี้การค้นภาษาไทยที่ล้านบทความได้ p95 69 ms และ load test เผยข้อควรระวังสองข้อ:

- **trigram ต้องการอย่างน้อยสามตัวอักษร** การค้นหนึ่งหรือสองตัวอักษรใช้ index ไม่ได้และต้องอ่านทุกแถว การค้นตัวเลข 1 ถึง 3 หลักยังได้ p95 2.7 วินาที
- **`LC_CTYPE` ของฐานข้อมูลมีผล** ถ้าเป็น `C` แล้ว `pg_trgm` จะไม่นับอักษรไทยเป็นตัวอักษร และ index แทบไม่ช่วยอะไร ตอนนี้ Easy CMS เตือนตอนเริ่มเมื่อเจอกรณีนี้

## แก้ที่ 4: ให้ CDN ตอบแทน (1.11)

request ส่วนใหญ่ที่เข้า CMS คือการอ่านเนื้อหาที่ publish แล้ว และเหมือนกันสำหรับทุกคน แทนที่จะมี cache ในแอป ตอนนี้ Easy CMS ส่ง header สำหรับ HTTP caching ได้: `s-maxage`, `stale-while-revalidate`, `ETag` แบบ weak และ cache tag (`ecms:posts:42`) เมื่อบันทึก publish หรือลบบทความ จะเรียก `purge` พร้อม tag ที่เปลี่ยน ซึ่งใน Next.js ก็คือ `revalidateTag`

request ที่มีการ login, session, API key หรือฉบับร่าง ยังเป็น `no-store` ถ้าตรงนี้ผิด ฉบับร่างของคนหนึ่งจะไปโผล่ให้ทุกคนเห็น กฎจึงตั้งใจทำให้แคบ

## สิ่งที่ไม่ได้เพิ่ม: Redis

ทุกขั้นตอนมีคำตอบแบบ "เพิ่ม Redis สิ": cache ด้วย Redis คิวงานด้วย Redis rate limit ด้วย Redis แต่ละอย่างคือ server อีกตัวสำหรับทุกทีมที่ self-host

ผมเลือกเขียนการตัดสินใจไว้แทน:

- คิวงานยังอยู่ใน Postgres (หรือ SQLite) โดยหยิบงานด้วย `UPDATE` แบบมีเงื่อนไข ([บทความก่อนหน้า](/th/blog/postgres-job-queue-th) อธิบายวิธีไว้)
- cache ไปอยู่ที่ HTTP และ CDN ที่ทีมมีอยู่แล้ว
- ถ้าวันหนึ่งผลวัดบอกว่าต้องมี Redis จริง จะมาเป็น adapter แบบเลือกใช้

แนวคิดเดียวกันนี้ทำให้ 1.12 มี **outbox**: after hook, webhook และการ purge cache ถูกเขียนลงใน transaction เดียวกับการบันทึก แล้ว worker รันและ retry ให้ การ purge ที่ล้มจะไม่ทิ้งหน้าเก่าค้างไว้จนกว่าจะมีคนสังเกตอีกต่อไป

## Search และบั๊กของสระอำ (1.13)

trigram index หาส่วนของข้อความได้ แต่การเรียงตามความเกี่ยวข้องข้ามหลาย field และหลาย collection ต้องใช้ search engine 1.13 จึงเพิ่ม interface สำหรับ search adapter และ adapter ตัวแรก `memorySearch()` สำหรับ dev และเว็บเล็ก ตัดคำด้วย `Intl.Segmenter` ซึ่งใช้การตัดคำแบบพจนานุกรมของ ICU ที่มากับ Node: `ข่าวน้ำท่วมกรุงเทพมหานคร` กลายเป็น ข่าว | น้ำ | ท่วม | กรุงเทพมหานคร

เวอร์ชันแรก normalize ข้อความด้วย NFKC ก่อนตัดคำ ตามที่มักทำกันเพื่อให้เทียบข้อความได้ แล้ว test ที่ค้น `น้ำท่วม` ก็ล้ม เพราะ NFKC แยกสระอำ (ำ) ออกเป็นสองตัว คือนิคหิตกับสระอา ข้อความดูเหมือนเดิม แต่พจนานุกรมของ ICU ไม่รู้จักคำนั้นอีกต่อไป `ข่าวน้ำท่วม` จึงออกมาเป็น ข่า | วน้ํา | ท่วม ส่วน NFC เก็บสระอำไว้ทั้งตัว ถ้าคุณ normalize ข้อความไทยก่อนค้น ให้ใช้ NFC

## ตัวเลขตอนนี้

บนรุ่น 1.10 ส่ง request พร้อมกัน 20 ตัวต่อชนิด:

- อ่านบทความตาม id หรือ slug: **22 ms** (p95)
- หน้าแรกของ list: **28 ms**
- หน้าถัดไปด้วย cursor ลึกเข้าไปใน list: **29 ms**
- ค้นภาษาไทยด้วย `like` และ trigram index: **69 ms**
- บันทึกฉบับร่างพร้อมเวอร์ชัน: **89 ms**

![กราฟแท่ง p95 ที่ 1,000,000 บทความ สเกล log: การอ่านตาม slug, cursor และการค้นภาษาไทยต่ำกว่า 100 ms ส่วนการกรอง relationship การค้นตัวเลข หน้าลึก และการค้นในบล็อกอยู่ที่ 1.4 ถึง 6.7 วินาที](/images/blog/scale-1m/diagram-1.th.png)

ตอนมี editor 200 คน การอ่านลดจาก p95 ราว 30 วินาทีเหลือ 17 วินาที ดีขึ้นแล้ว แต่ยังห่างจากคำว่าดีอีกมาก

## อะไรที่ยังช้า

- **กรองด้วย relationship แล้วเรียงตามวันที่:** p95 1.4 วินาที
- **query ภายในบล็อก** (`layout.blockType`): p95 6.7 วินาที บล็อกเก็บเป็น JSON และยังไม่มี index สำหรับ path นี้
- **หน้าลึกตามเลขหน้า:** 5.6 วินาที ใช้ cursor แทน
- **การบันทึกในโหลดผสม:** p95 30 วินาที เพราะต้องรอ connection ที่การอ่านช้าๆ ถือไว้

[คู่มือฐานข้อมูล](/th/docs/databases#at-1-000-000-posts) มีตัวเลขทั้งหมด และทุกตัวเลขในบทความนี้มาจากที่นั่นหรือจาก workflow การวัดก่อนเปลี่ยนสิ่งที่ผมสร้าง ผมคาดว่าฐานข้อมูลจะเป็นขีดจำกัด แต่จริงๆ แล้วเป็น query ไม่กี่แบบที่ถือ connection ไว้ และการแก้แต่ละอย่างนับว่าสำเร็จก็ต่อเมื่อตัวเลขของคืนถัดไปขยับ

ถ้าคุณรัน Easy CMS หรือแอป Node.js บน Postgres ที่มีตารางใหญ่ ผมอยากรู้ว่า query ที่ช้าของคุณหน้าตาเป็นอย่างไร: [GitHub discussions](https://github.com/maritonx/easy-cms/discussions)
